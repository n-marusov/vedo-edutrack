## 2. Ответ (Best-Practice Answers)

### A1. Аварийные сценарии CI/CD (ячейка 4.1)

**Ответ:** CI/CD-пайплайн обязан иметь процедуры восстановления при аварийных сценариях: падение пайплайна, недоступность VCS, сбой деплоя, потеря артефактов — с измеримыми целями восстановления (MTR) и гарантией воспроизводимости сборки.

**Измеримые критерии:**
- Восстановление пайплайна: при падении CI/CD инфраструктуры полное восстановление работоспособности пайплайна ≤ 2 часов (MTR).
- Недоступность VCS: восстановление доступа к репозиториям ≤ 1 часа; данные VCS (репозитории, история) имеют резервную копию с RPO ≤ 24 часов.
- Сбой деплоя: автоматическая остановка деплоя при сбое и откат к последней стабильной версии ≤ 15 минут (согласуется с REQ-NFR-ops.release.deployment-verification и canary-kill-switch).
- Потеря артефактов: артефакты сборки хранятся в artifact registry с retention ≥ 180 дней; повторная сборка из зафиксированного коммита даёт идентичный артефакт (детерминированная сборка, см. cicd-supply-chain-security).
- Дрилл: симуляция падения CI/CD выполняется ≥ 1 раза в квартал; фактический MTR фиксируется в отчёте.

### A2. Изоляция окружений разработки (ячейки 1.1, 2.1)

**Ответ:** Окружения dev/staging/prod обязаны быть изолированы, а production-данные (особенно ПДн) не должны попадать в dev-окружения, поскольку утечки через незащищённые среды разработки — регулярный инцидент безопасности.

**Измеримые критерии:**
- Сегментация: dev/staging/prod — изолированные сети/аккаунты; отсутствие прямого сетевого пути prod→dev (0 открытых портов, проверка сетевым сканом).
- Production-данные в dev: использование реальных ПДн в dev/staging запрещено; используется синтетика или анонимизированные данные; проверка — сканер чувствительных данных в dev-БД = 0 совпадений с реальными ПДн.
- Доступ: разработчики имеют доступ к dev/staging; доступ к prod — по REQ-NFR-ops.access.production-control (read-only/JIT).
- Онбординг разработчика: окружение поднимается по REQ-NFR-process.dev.engineering-gates (`make up` ≤ 30 мин) без доступа к prod-секретам; секреты dev-окружения отдельны от prod (0 общих секретов).

### A3. Откат миграций БД (ячейка 4.3)

**Ответ:** Обновление схемы БД обязано иметь обратимые миграции (forward/backward) с автоматическим откатом при сбое, поскольку неудачная миграция без rollback приводит к потере данных и простою.

**Измеримые критерии:**
- Каждая миграция имеет обратимый шаг (down-migration): 100% миграций поддерживают откат; непокрытые откатом миграции запрещены (гейт в CI).
- Автоматический откат: при сбое миграции (ошибка, частичное применение) система автоматически откатывает к предыдущей схеме ≤ 15 минут без ручного вмешательства.
- Тест обратимости: для каждой миграции выполняется up→down→up тест в CI; 100% миграций проходят (0 сбоев).
- Откат миграции не нарушает целостность данных: после rollback расхождение контрольных сумм с точкой до миграции = 0 (согласуется с REQ-NFR-data.availability.backup-validity).
- Миграции применяются в окно сопровождения; изменение схемы без обратимого шага блокирует релиз.
