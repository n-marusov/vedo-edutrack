## 2. Ответ (Best-Practice Answers)

### A1. Пользовательская документация и обучение (ячейка 5.2)

**Ответ:** Система обязана иметь пользовательскую документацию и встроенный онбординг, поскольку vision 3.1 фиксирует «простота для родителя» как критический фактор, а критерий успеха G1/G2 — «без чтения документации». Документация — часть компетенций пользователя для эксплуатации.

**Измеримые критерии:**
- Встроенный онбординг: новый пользователь строит первый маршрут ≤ 5 минут от входа (совпадает с G3) — проверяется юзабилити-тестом ≥ 5 новых пользователей на релиз.
- Пользовательская документация: справочные статьи покрывают 100% пользовательских сценариев F1–F5 (маршрут, план-факт, лакуны, ФГОС, ресурсы); поиск по документации работает ≤ 2 сек.
- Документация обновляется при каждом изменении функциональности: 100% релизов с изменением UX сопровождаются обновлением документации (гейт в CI).
- Обучающие материалы (видео/статьи) для ролей: родитель, ученик, методист, HR; покрытие ролей = 100%.

### A2. Аварийные сценарии вывода из эксплуатации и миграции (ячейки 2.4, 1.4, 4.4)

**Ответ:** Система обязана иметь процедуры и UX для аварийных сценариев вывода из эксплуатации: частичная миграция, потеря данных при сбое, зависшие транзакции — с измеримыми гарантиями целостности и эргономичным интерфейсом администратора.

**Измеримые критерии:**
- При сбое миграции система переходит в консистентное состояние: частично мигрированные данные не теряются (транзакционная миграция или восстановимая контрольная точка); потеря данных при сбое миграции = 0.
- Зависшие транзакции при миграции/деактивации разрешаются автоматически: 100% зависших операций завершаются или откатываются ≤ 24 часов; пользователь видит статус операции (см. REQ-NFR-data.compliance.pii-export-deletion).
- UX администратора при деактивации: консоль администратора отображает статус каждого шага вывода (уведомление, экспорт, отзыв, архив) с прогрессом; 100% шагов отслеживаемы.
- Тест: симуляция сбоя миграции (обрыв на 50% данных) → целостность данных = 100% (расхождение = 0), повторный запуск миграции успешен.

### A3. Мониторинг бизнес-метрик продукта (ячейки 3.3, 4.2)

**Ответ:** Система обязана мониторить бизнес-метрики продукта как наблюдаемые SLO: точность прогноза аттестации (±10% из G4), покрытие ФГОС (G1), качество диагностики лакун, — поскольку целевые бизнес-показатели без механизма измерения и алертинга неконтролируемы.

**Измеримые критерии:**
- Точность прогноза: фактическая точность бинарного прогноза «успевает/не успевает» ≥ 90% (допуск ±10% из vision G4); метрика публикуется ежемесячно в observability-дашборд.
- Покрытие ФГОС: доля активных пользователей с актуальным (≤ 24 ч) расчётом покрытия ≥ 95%; задержка расчёта покрытия p95 ≤ 1 сек (см. REQ-NFR-api.performance.latency-p95).
- Метрика качества диагностики лакун: доля диагностик, подтверждённых пользователем как полезные, ≥ 70% (измеряется по feedback).
- Алертинг по бизнес-метрикам: отклонение точности прогноза > 10% от целевой в течение месяца → P2-алерт владельцу продукта (см. REQ-NFR-ops.observability.alerting-escalation).

## 3. Требования (Materialized as REQ-NFR specs)

Три новых NFR-файла создаются в `specs/requirements/`:

1. `REQ-NFR-ops.compliance.user-documentation` (P1) — пользовательская документация, онбординг, обучение
2. `REQ-NFR-data.compliance.decommissioning-safety` (P1) — аварийные сценарии вывода и миграции, UX администратора

Все требования соответствуют конвенциям `REQ-NFR-<area>.<qualifier>.<attribute>`, имеют обязательные поля и измеримые критерии приёмки.
