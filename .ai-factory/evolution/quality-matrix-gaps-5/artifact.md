## 2. Ответ (Best-Practice Answers)

### A1. Масштабируемость под нагрузку (ячейки 5.3, 3.2)

**Ответ:** Система обязана масштабироваться горизонтально с измеримыми гарантиями под кратный рост нагрузки, поскольку vision G2 требует «тысячи персональных маршрутов параллельно», а отказ при пике (окна аттестаций) критичен для бизнеса.

**Измеримые критерии:**
- Нагрузочный тест на кратный рост: система выдерживает 10× пиковую нагрузку относительно базовой (1000 concurrent из REQ-NFR-api.performance.latency-p95) без деградации p95 более чем на 50%.
- Горизонтальное масштабирование: сервисы stateless и масштабируются добавлением нод; автоскейлинг по CPU/очереди: добавление ноды ≤ 5 минут от превышения порога.
- Capacity plan: документированный план ёмкости на рост до 10× текущих пользователей; пересматривается ≥ 1 раза в квартал.
- Деградация при перегрузке: при превышении ёмкости система деградирует предсказуемо (rate limiting, очередь), не теряя данные (0 потерь при перегрузке).
- Пиковые окна: производительность в пиковые окна (аттестации — май) не ниже базовой: p95 ≤ 200 мс при 1000 concurrent (согласуется с latency-p95).

### A2. Защита архивных данных при выводе (ячейка 4.4)

**Ответ:** Архивные данные при выводе из эксплуатации обязаны быть защищены: шифрование, контроль доступа, аудит обращений — чтобы предотвратить несанкционированный доступ к архивам после остановки сервиса.

**Измеримые критерии:**
- Шифрование архивов: все архивные данные (логи, выгрузки, бэкапы) хранятся в зашифрованном виде (AES-256); чтение архивов без ключей = 0 доступов (тест на копии).
- Контроль доступа к архивам: доступ к архивным данным — только по 2-person rule (см. REQ-NFR-ops.access.production-control); 100% обращений к архивам аудируются.
- Сроки хранения архивов: соответствуют REQ-NFR-data.compliance.retention-policy; по истечении — автоматическое удаление.
- Аудит обращений: журнал обращений к архивам хранится без ПДн (анонимизированный); 0 неавторизованных обращений (тест).
- Архивные данные не доступны из публичных эндпоинтов после остановки сервиса: 0 открытых путей (проверка сканом).

### A3. Документация разработчика и передача знаний (ячейка 2.1)

**Ответ:** Проект обязан иметь документацию разработчика и процедуры передачи знаний, поскольку отсутствие архитектурной документации замедляет онбординг, увеличивает bus-factor и риск потери знаний при уходе сотрудника.

**Измеримые критерии:**
- Архитектурная документация: актуальная документация архитектуры (C4/компоненты) покрывает 100% сервисов и ключевых потоков; обновляется при каждом архитектурном изменении (гейт: PR с архитектурным изменением обязан обновлять документацию).
- Навигация по коду: README каждого модуля/сервиса содержит назначение, структуру, ключевые сценарии; покрытие модулей = 100%.
- Передача знаний: runbook'и и документация покрывают 100% критичных операций (деплой, откат, восстановление) — согласуется с REQ-NFR-process.dev.engineering-gates.
- Bus-factor: для каждого критичного компонента ≥ 2 разработчика знакомы с ним (проверка: матрица знаний); документация позволяет новому разработчику выполнить онбординг ≤ 1 недели.
- Документация разработчика хранится в репозитории (рядом с кодом) и проходит код-ревью: 100% обновлений документации — через PR.

## 3. Требования (Materialized as REQ-NFR specs)

Три новых NFR-файла создаются в `specs/requirements/`:

1. `REQ-NFR-ops.performance.scalability` (P1) — масштабируемость, capacity plan, автоскейлинг
2. `REQ-NFR-data.compliance.archive-security` (P1) — защита архивных данных при выводе
3. `REQ-NFR-process.dev.developer-documentation` (P1) — документация разработчика и передача знаний

Все требования соответствуют конвенциям `REQ-NFR-<area>.<qualifier>.<attribute>`, имеют обязательные поля и измеримые критерии приёмки.
