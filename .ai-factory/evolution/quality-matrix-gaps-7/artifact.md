## 2. Ответ (Best-Practice Answers)

### A1. Регуляторные ограничения процесса разработки (ячейка 1.1)

**Ответ:** Процесс разработки обязан учитывать регуляторные и корпоративные ограничения среды: экспортные ограничения, отраслевые регламенты, требования к среде разработки — с документированным реестром применяемых ограничений и проверкой соответствия.

**Измеримые критерии:**
- Реестр ограничений: документированный перечень регуляторных/корпоративных ограничений на разработку (лицензии, экспортные ограничения, отраслевые стандарты); обновляется при изменении; актуальность = 100%.
- Соответствие: CI-проверка соответствия разрабатываемого кода ограничениям (например, запрещённые библиотеки/паттерны) — 0 нарушений = гейт релиза.
- Экспортные ограничения: используемые компоненты проверяются на экспортные ограничения (EAR/ITAR для РФ — санкционные списки); 0 нарушений.
- Отраслевые регламенты: для образовательного домена — требования к обработке данных несовершеннолетних учитываются в процессе разработки (проектирование с защитой по умолчанию).

### A2. Когнитивная нагрузка кода (ячейка 2.1)

**Ответ:** Код обязаен соответствовать лимитам когнитивной сложности: цикломатическая сложность, размер функций, глубина вложенности — поскольку высокая сложность увеличивает дефектность и замедляет ревью.

**Измеримые критерии:**
- Цикломатическая сложность: CC ≤ 10 для 100% функций (гейт в CI); функции с CC > 15 требуют рефакторинга.
- Размер функций: 100% функций ≤ 60 строк (или эквивалент для языка); превышение — ревью-гейт.
- Глубина вложенности: ≤ 4 уровня для 100% кода (гейт в CI).
- Метрики сложности публикуются в отчёте CI; регрессия сложности (рост средней CC) > 10% между релизами блокирует релиз.
- Согласуется с engineering-gates (линтеры) — метрики сложности добавляются к существующим гейтам.

### A3. Эргономика консолей администрирования (ячейка 2.3)

**Ответ:** Консоли администрирования обязаны соответствовать эргономическим требованиям: скорость выполнения частых операций, понятность статусов, защита от ошибочных деструктивных действий — чтобы операторы работали быстро и без ошибок.

**Измеримые критерии:**
- Скорость частых операций: типовые операции администратора (просмотр статуса, поиск записи, сброс пароля) выполняются ≤ 30 секунд (p95); измеряется юзабилити-тестом.
- Статусы: консоль отображает статус всех систем/сервисов одним экраном (согласуется с golden-signals); время до полной картины ≤ 5 секунд.
- Защита от ошибок: деструктивные действия (удаление, массовое изменение) требуют подтверждения (двойной ввод/подтверждающий диалог); 100% деструктивных операций защищены.
- Понятность: консоль переведена на язык UI (русский), термины соответствуют глоссарию; 100% действий имеют понятные подписи.
- Согласуется с production-control (2-person rule для деструктивных операций) и alerting-escalation.

### A4. Компетенции пользователя и клиентская инфраструктура (ячейка 5.2)

**Ответ:** Пользователи обязаны иметь обучение и документацию для эксплуатации, а система — требования к клиентской инфраструктуре, поскольку vision 3.1 фиксирует разные уровни подготовки пользователей (родитель без подготовки, методист, HR).

**Измеримые критерии:**
- Обучение: ролевые обучающие материалы (родитель, ученик, методист, HR) покрывают 100% ролей; для Enterprise — обязательный онбординг-тренинг перед передачей в эксплуатацию.
- Клиентская инфраструктура: документированные требования к клиентским устройствам и сети (см. supported-browsers: браузеры, ОС, ≥ 1 Мбит/с); проверка совместимости при первом входе.
- Документация для эксплуатации: инструкции по частым операциям (построение маршрута, экспорт, отчёт) доступны из интерфейса ≤ 2 кликов (согласуется с user-documentation).
- Обратная связь по обучению: эффективность обучения измеряется (доля пользователей, выполнивших целевое действие после обучения, ≥ 80%).
