# Integration tests insert non-UUID plan ids into uuid columns

**Date:** 2026-08-03 21:15
**Files:** backend/tests/repository_executionprogress_test.go, backend/tests/repository_gapcoverage_test.go
**Severity:** medium

## Problem

`go test -tags=integration ./...` (delivery gate `go-test-integration`, T16) failed with 4 real
test failures — SQLSTATE 22P02 (invalid input syntax for type uuid):

- TestProgressRepositoryUpsertAndList: `upsert module progress ... invalid input syntax for type uuid: "plan-progress-1"`
- TestProgressRepositoryDeviationEventDedup: `insert deviation event: ... "plan-progress-2"`
- TestProgressRepositoryReadinessForecast: `insert readiness forecast: ... "plan-progress-3"`
- TestGapRepositorySaveAndListAnalysis: `insert gap diagnostic: ... "plan-gap-1"`

The failures surfaced as a `warn` in the delivery gate summary (advisory at M0.2), which is why
`make check` printed FAIL banners while still exiting 0.

## Root Cause

The executionprogress/gapcoverage migrations define `plan_id uuid NOT NULL` (with
`gen_random_uuid()` for primary keys). The repository integration tests used human-readable
string ids ("plan-progress-1", "plan-gap-1") as fixture values. pgx passes the string straight
into the `uuid` parameter and PostgreSQL rejects any non-UUID literal with 22P02.

The planmanagement path does not hit this because `PlanRepository.SavePlan` deliberately omits
the client-provided id and lets the DB generate a UUID (`RETURNING id`) — the app-level
`FixationRequest.PlanID` ("plan-1") is a logical id that is never persisted. The progress/gap
repositories, in contrast, insert `plan_id` verbatim, so the tests must supply real UUIDs.

## Solution

Replaced the non-UUID fixture ids with valid UUID constants (same style as the learner ids
already in the tests):

- `"plan-progress-1"` → `77777777-7777-7777-7777-777777777777`
- `"plan-progress-2"` → `88888888-8888-8888-8888-888888888888`
- `"plan-progress-3"` → `99999999-9999-9999-9999-999999999999`
- `"plan-gap-1"`     → `aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa`

Added short comments on the first occurrence explaining that `plan_id` is a uuid column so the
fixture must be a valid UUID (prevents reverting to readable strings).

## Prevention

- Integration-test fixtures against PostgreSQL must match the column type: `uuid` columns get
  real UUIDs, `text` columns get readable strings. Check the migration before writing fixtures.
- Run `go test -tags=integration ./...` (or `make check` / the `go-test-integration` gate) after
  adding repository tests — unit (`go test ./...`) does not cover the tagged files.
- Consider a schema-wide ID policy: `learning_plans.id` is a DB-generated uuid while the app
  layer treats PlanID as an opaque string (`FixationRequest.PlanID` is required but never
  stored). Documenting or reconciling this (ADR or `specs/ddd/aggregates.md`) would prevent
  future mismatches.

# Frontend T14 scaffold tests skip unimplemented features

**Date:** 2026-08-03 21:20
**Files:** frontend/src/features/{identity-access,plan-management,integrations,visualization,practice-life}/__tests__/*.test.tsx, frontend/src/shared/__tests__/shared.test.tsx
**Severity:** low

## Problem

`pnpm test` (vitest, delivery gate `vitest`, T16) failed with 6 red scaffold tests — every
unimplemented feature placeholder used `expect.fail('TODO: implement ...')`, which fails the
suite and prints FAIL banners in `make check`.

## Root Cause

The T14 component-test scaffolds for features that are not implemented yet (identity-access,
plan-management, integrations, visualization, practice-life, shared design-system) were written
as hard-failing `expect.fail` stubs. At M0.2 the `vitest` gate is advisory so the run still
exits 0, but the FAIL output is noise and the pattern was applied inconsistently — e2e stubs
(`tests/e2e/gui/tests/mvp-must-scenarios.spec.ts`) already used `test.skip`, while the frontend
scaffolds failed instead.

## Solution

Converted all 6 scaffold tests from `it(... expect.fail(...))` to `it.skip(...)` with the TODO
(US/UC references and target milestone) preserved as a comment inside the body. Removed the now
unused `expect` import. Vitest reports them as skipped: 17 passed | 6 skipped | 0 failed, gate
turns green.

## Prevention

- For features not yet implemented, scaffolds should use `it.skip` / `test.skip` (keep the TODO
  comment), not `expect.fail` — a red scaffold fails the whole suite and hides real regressions.
- When the feature lands, replace the skip with a real render/behavior assertion and remove the
  TODO comment (gates.yaml marks the vitest gate blocking from M0.3).
- Follow the established e2e pattern (`test.skip` + TODO) across all test layers.
