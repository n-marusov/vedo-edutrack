# Go coverage tool cannot resolve module paths on Windows from project root

**Date:** 2026-08-04 02:30
**Files:** deploy/ci/coverage-check.sh
**Severity:** medium

## Problem

`coverage-check.sh` gate (REQ-NFR-process.dev.test-coverage) always failed to
parse the coverage profile on Windows. The `go tool cover -func` command could
not resolve the Go module import paths (`vedo-edutrack/backend/...`) stored in
the coverage file, because it was invoked from the project root while the Go
module lives under `backend/`. The error manifest as:

```
cover: package vedo-edutrack/backend/... is not in std (C:\Program Files\Go\src\...)
```

The script would silently fall through to `exit 0` with an unhelpful
"could not parse" message, masking the actual coverage number.

## Root Cause

The coverage file was generated inside `backend/` (via `cd backend && go test
-coverprofile=coverage.out ./...`) but consumed from the project root with the
full relative path (`go tool cover -func=backend/coverage.out`). `go tool
cover` resolves the import paths in the coverage file relative to the module
root, but when called from outside the module directory, it cannot match them
to any package in GOPATH/GOROOT — a behavior that differs between Unix (where
tool cover is more lenient) and Windows (strict).

## Solution

Extracted the directory component from `$FILE` before invoking `go tool cover`,
then `cd` into that directory so Go can resolve the module:

```bash
COVER_DIR="$(dirname "$FILE")"
COVER_FILE="$(basename "$FILE")"
TOTAL="$(cd "$COVER_DIR" && go tool cover -func="$COVER_FILE" 2>/dev/null | tail -1 | ...)"
```

This is backward-compatible:
- `FILE=backend/coverage.out` → `cd backend && go tool cover -func=coverage.out`
- `FILE=coverage.out` → `cd . && go tool cover -func=coverage.out` (unchanged)
- `FILE=/abs/path/to/coverage.out` → works if the dir is a Go module root

## Prevention

- Always run Go tooling (`go tool cover`, `go vet`, etc.) from the module
  directory, not from a parent project root
- When a script accepts a file path that crosses module boundaries, extract the
  directory and `cd` before invoking Go tooling
- Test shell scripts on both Unix and Windows — `go tool cover` behavior
  differs: Unix is more forgiving of module path resolution from outside the
  module; Windows is strict
