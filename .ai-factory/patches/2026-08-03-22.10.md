# Verbose error leak in GetLearnerForecast handler

**Date:** 2026-08-03 22:10
**Files:** backend/internal/api/handler.go, backend/internal/api/handler_contract_test.go
**Severity:** medium

## Problem

`GET /learners/{learner_id}/forecast` returned the raw Go error string
(`err.Error()`) to the client in a 500 response. In production, a database or
service failure would expose internal implementation details (connection
strings, SQL fragments, file paths) to API consumers.

Found by `/aif-security-checklist` (OWASP A05 — verbose errors; checklist item
"error messages don't leak sensitive info").

## Root Cause

The handler was written as a thin pass-through of the application-layer error:
`msg := err.Error()` then `ErrorResponse{Error: "forecast_failed", Message: &msg}`.
The intent was a stable error code (`forecast_failed`), but the message field
carried the full internal error. This is a common quick-wiring mistake: the
error code is client-safe while the message accidentally leaks internals.
Additionally, `RecordModuleMastered` accepted empty `module_id` and arbitrary
`status` values — no input validation on a state-changing endpoint.

## Solution

1. `GetLearnerForecast`: log the full error server-side with context
   (`h.Logger.Error("forecast computation failed", zap.String("learner_id", ...), zap.Error(err))`)
   and return a stable, generic client-safe message `"forecast computation failed"`
   with the existing `forecast_failed` code. No internal details reach the client.
2. `RecordModuleMastered`: added input validation — reject empty `module_id`
   (400) and statuses outside `{in_progress, mastered, skipped}` (400).
3. Added 5 contract tests covering: valid mastery recording (201), empty
   module_id rejected (400), invalid status rejected (400), forecast endpoint
   returns a valid status (200), module stories endpoint returns expected data.

## Prevention

- When writing HTTP handlers, treat `ErrorResponse.Message` as a **client-safe
  string**, never a raw `err.Error()`. The full error belongs in the server log
  (zap) only.
- State-changing endpoints must validate required fields and enum values before
  acting; empty-string checks are the minimum.
- The security checklist's "verbose errors" item is a lint-relevant review
  check: grep for `err.Error()` inside `writeJSONBody`/`ErrorResponse{...}`
  before commit.
- Contract tests should cover both happy path and rejection cases for every new
  state-changing endpoint.
