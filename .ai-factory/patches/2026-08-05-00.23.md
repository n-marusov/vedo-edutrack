# Dev backend container unhealthy due to Go module cache not preloaded

**Date:** 2026-08-05 00:23
**Files:** deploy/backend.Dockerfile, deploy/docker-compose.yml
**Severity:** high

## Problem

`vedo-edutrack-backend-1` container was unhealthy on every `make up`. The
Docker healthcheck (`wget http://localhost:8080/healthz`) failed because the
Go server never started. `make up` exited with `[FAIL] dev stack failed to
start`.

Direct symptom from container logs: air repeatedly failed to build the binary:
```
go: proxy.golang.org: dial tcp: lookup proxy.golang.org on 192.168.65.7:53: server misbehaving
```

## Root Cause

Two independent issues combined into a single failure:

1. **GOPATH collision in Dockerfile.** The `deploy/backend.Dockerfile` did not
   set WORKDIR before `COPY backend/go.mod backend/go.sum ./`. In the
   `golang:1.26-alpine` base image the default WORKDIR is `/go`, which IS the
   GOPATH. Go deliberately ignores `go.mod` files placed inside GOPATH:
   `go: warning: ignoring go.mod in $GOPATH /go`. Since `go mod download` was
   a no-op, the Go module cache was never populated in the image layer.

2. **Docker Desktop DNS failure on Windows.** Docker Desktop for Windows
   (WSL2 backend) uses an embedded DNS resolver at `192.168.65.7:53` during
   builds and `127.0.0.11:53` at runtime. Neither could resolve
   `proxy.golang.org` — the host itself had a broken DNS server
   (`172.19.0.2`, likely from a VPN/corporate proxy). This meant every `go
   build` invocation by air had to download modules from scratch and failed.

The first issue was the blocker: even if DNS worked during `docker build`,
modules were not cached. The second issue was the visible symptom.

## Solution

### 1. Dockerfile: non-GOPATH WORKDIR before COPY (deploy/backend.Dockerfile)

Set WORKDIR to `/build-cache` (a clean directory outside GOPATH) BEFORE
copying `go.mod`/`go.sum` and running `go mod download`. The module cache
(`/root/go/pkg/mod`) is now populated at build time, survives the runtime
volume mount (`backend/ -> /app`), and air reuses it without network access.

```dockerfile
WORKDIR /build-cache
COPY backend/go.mod backend/go.sum ./
RUN go mod download
WORKDIR /app
```

### 2. DNS fallback (deploy/docker-compose.yml)

Added explicit Google DNS servers (`8.8.8.8`, `8.8.4.4`) to the backend
service. This provides a working fallback when Docker's embedded DNS or the
host DNS server fails — common on Windows with corporate VPNs.

```yaml
backend:
  dns:
    - 8.8.8.8
    - 8.8.4.4
```

## Prevention

- In Dockerfiles for Go projects, always set WORKDIR to a non-GOPATH
  directory before copying `go.mod`/`go.sum` and running `go mod download`.
  The default WORKDIR in `golang:*` images is `/go` (GOPATH) — Go will
  silently ignore go.mod there.
- If `go mod download` runs without error during `docker build`, it is NOT
  sufficient to verify modules were actually cached. Check that WORKDIR was
  set first, or run `ls /root/go/pkg/mod/cache/download/` after the `RUN go
  mod download` step to confirm cache population.
- On Windows Docker Desktop with VPN, consider adding `dns: 8.8.8.8` as a
  safety net for any compose service that needs external network access
  during development.
