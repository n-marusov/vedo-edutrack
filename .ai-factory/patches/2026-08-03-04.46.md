# Windows: make help fails with cmd.exe error — SHELL not resolved

**Date:** 2026-08-03 04:46
**Files:** Makefile
**Severity:** medium

## Problem

Running `make help` from PowerShell (native Windows GNU Make via chocolatey)
produced a cryptic Russian-language cmd.exe error:

```
Непредвиденное появление: -t.
make: *** [Makefile:51: help] Error 255
```

## Root Cause

The Makefile set `SHELL := /bin/bash` unconditionally. Native Windows GNU make
cannot resolve `/bin/bash` as a file path — it's a Unix-style absolute path
that has no meaning on a native Windows filesystem. Without a usable SHELL,
make falls back to cmd.exe, which cannot parse POSIX recipe syntax
(`[ -t 1 ]`, `&&`, `$$`, `grep`, `while`, etc.).

## Solution

Replaced `SHELL := /bin/bash` with an OS-conditional block (Makefile
lines 12–17). On Windows, set SHELL to `C:/Program Files/Git/bin/bash.exe`
(the Git-for-Windows bash, using forward slashes — native GNU make on
Windows accepts forward-slashed paths, and they avoid backslash-escaping
issues with `$(wildcard)` and `$(shell)`). On Linux/macOS, keep
`SHELL := /bin/bash`.

Key: forward slashes work; `$(firstword $(wildcard C:/Program\ Files/...))`
does NOT — wildcard returns the path with a literal backslash-escaped space
(`Program\ Files`), which is not a valid filesystem path for make's SHELL
execution. The direct forward-slashed path without escaping avoids this
pitfall entirely.

## Prevention

- Always use forward slashes in Windows paths passed to `SHELL` in
  Makefiles. Do not use `$(wildcard)` to discover bash.exe — its escaped-
  space return value breaks SHELL.
- Test `make help` on a native Windows GNU make instance (not MSYS2 make)
  to verify shell selection.
- ADR-IMPL.PROCESS.development-tooling §11 documents Windows tooling
  requirements.
