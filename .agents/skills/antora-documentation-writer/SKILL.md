# Скилл: «Технический писатель Antora»

## Краткое описание

Генерирует многокомпонентную техническую документацию в формате AsciiDoc, организованную для сборки через Antora в отдельные статические сайты (по аудиториям). **Автоматически учитывает проектные требования к документированию** из артефакта. Применяет правила качества текста (без «ридмитита» и снисходительных формулировок).

---

## Формат документации (дефолтный)

| Параметр | Дефолтное значение |
|----------|-------------------|
| Язык разметки | AsciiDoc (`.adoc`) |
| Сборщик | Antora |
| Навигация | `nav.adoc` для каждого компонента |
| Мета-файлы | `antora.yml` (версия, компонент, название) |

---

## Структура выходных данных (дефолтная)

```
docs/antora/
├── {component-1}/
│   ├── antora.yml
│   ├── modules/ROOT/
│   │   ├── nav.adoc
│   │   └── pages/
│   │       ├── index.adoc
│   │       └── ...
├── {component-2}/
├── playbook-{component-1}.yml
├── playbook-{component-2}.yml
├── update.md
└── review-checklist.md
```

### Компоненты по умолчанию

| Компонент | Аудитория | Аутентификация |
|-----------|-----------|----------------|
| `user-guide` | конечные пользователи | нет |
| `developer-guide` | разработчики, архитекторы | роль Developer |
| `admin-guide` | DevOps, администраторы | требуется вход |
| `integrator-guide` | интеграторы, партнёры | роль Developer/Partner |

Запрещены перекрёстные ссылки между компонентами.

> **Примечание:** пользователь может переопределить список компонентов.

### Обязательные параметры

| `artifacts_path` | Путь к папке с артефактами требований и архитектуры | `human/artifacts` |

| Параметр | Описание | Дефолтное значение |

## Правила качества документации (дефолтные)

### Запрещённые слова

`легко`, `просто`, `тривиально`, `безболезненно`, `всего лишь`, `очевидно`, `естественно`, `несложно`

### Конкретика

- Все единицы измерения явно: `timeout_ms`, `size_bytes`, `memory_mb`
- Типы параметров, диапазоны, значения по умолчанию
- Никаких «много», «быстро», «недавно» — только числа или конкретные пороги

### Структура AsciiDoc для Antora

- Каждая страница: `= Заголовок` + мета-описание
- `==`, `===` для подразделов
- Обязательная навигация `nav.adoc`
- Для длинных документов — `:toc: left` или `:toc: macro`

### Примеры и антипримеры

- Рабочий пример кода/команды для каждой инструкции
- Антипример с пояснением для типичных ошибок

### Предупреждения

- Недокументированное поведение помечать: `[WARNING]` и фразой «Может измениться без предупреждения»
- Предварительные требования выносить в отдельный раздел

### Стилистика (анти-«ридмитит»)

- Нет латинизмов без расшифровки (`per se`, `de facto`, `a priori`)
- Нет панибратства («итак, народ», «как вы уже догадались»)
- Активный залог вместо пассивного

### Offline-совместимость

- Никаких внешних CDN, unpkg, cdnjs
- Все ресурсы — локальные или опциональные

### Обязательные разделы документа

`Введение`, `Предварительные требования`, `Основная инструкция/описание`, `Примеры`

| Приоритет | Источник |

| 3 (низший) | Дефолтные настройки скилла |

## Шаги

### Шаг 1: Поиск и загрузка проектных требований

**Перед генерацией любой документации** скилл выполняет поиск артефакта с требованиями к документированию.

**Что делает скилл:**

1. Сканирует папку `artifacts_path` в поиске файлов со следующими паттернами имён (регистронезависимо):
   - `*документация*`, `*documentation*`
   - `*doc-requirements*`, `*docreq*`
   - `*specification*` (если внутри есть раздел про документацию)
   - Любой файл, на который есть ссылка в CI-инструкциях проекта

2. **Если файл найден:**
   - Читает его содержимое
   - Извлекает секции, относящиеся к требованиям документации (структура, форматы, аудитории, политики доступа, версионирование, offline-требования)
   - Применяет их как приоритетные (переопределяют дефолтные настройки скилла)

3. **Если файл не найден:**
   - Запрашивает у пользователя: *«Не найден артефакт с требованиями к документированию. Пожалуйста, укажите путь к такому файлу (если он есть) или разрешите использовать дефолтные требования скилла.»*
   - Пользователь может:
     - Предоставить файл
     - Подтвердить использование дефолтных требований
     - Ввести требования вручную (краткий список)

4. **Если найдено несколько файлов:**
   - Показывает пользователю список найденных файлов
   - Запрашивает, какой из них является актуальным (или нужно ли объединить)
   - При объединении — мержит параметры (при конфликтах приоритет у файла с более поздней датой изменения)

---

### Шаг 2: Чтение артефактов

**Что делает скилл:**

1. Сканирует папку `artifacts_path` (исключая файл требований, который уже обработан на Шаге 1)
2. Читает содержимое каждого файла из `source_files` (или всех найденных, если список не указан)
3. Определяет тип каждого артефакта:
   - API-спецификация (OpenAPI, GraphQL, gRPC)
   - ADR (Architecture Decision Record)
   - Архитектурная схема (C4, PlantUML, Mermaid)
   - Runbook (инструкция по эксплуатации)
   - Пользовательская история
   - Контракт интеграции
4. Если для полноты документации не хватает артефактов — скилл **запрашивает их у пользователя**, а не домысливает.

---

### Шаг 3: Маппинг артефактов на компоненты

**Что делает скилл:**

1. Использует список компонентов из:
   - Проектных требований (если найдены на Шаге 1)
   - Либо дефолтный список (`user-guide`, `developer-guide`, `admin-guide`, `integrator-guide`)

2. Распределяет каждый артефакт по компонентам по следующим правилам:

| Тип артефакта | Куда направляется |
|---------------|-------------------|
| API-спецификация | `developer-guide` + `integrator-guide` |
| ADR | `developer-guide` |
| Архитектурная схема | `developer-guide` |
| Runbook (установка, мониторинг, бэкапы) | `admin-guide` |
| Пользовательские сценарии, интерфейс | `user-guide` |
| Webhook, OAuth, SDK | `integrator-guide` |

3. Если артефакт не подходит ни к одному из заданных компонентов:
   - Предлагает пользователю создать новый компонент
   - Либо сообщает, что артефакт не требуется документировать (если требования это явно разрешают)

---

### Шаг 4: Генерация AsciiDoc-файлов

**Что делает скилл:**

Для каждого компонента создаёт:

1. **Главную страницу** `index.adoc` с обзором компонента

2. **Отдельные `.adoc` файлы** по темам (по одному на каждый артефакт или логический раздел)

3. **Файл навигации** `nav.adoc`

**Формат каждой страницы:**

```asciidoc
= Название
:description: Краткое описание страницы
:keywords: ключевые, слова

== Введение

текст текст текст

== Предварительные требования

* Требование 1
* Требование 2

== Основная инструкция

. Шаг 1
. Шаг 2

[source,bash]
----
пример команды
----

[WARNING]
====
Предупреждение, если нужно
====

== Примеры

=== Рабочий пример
...

=== Антипример (как не надо)
...
```

**Обязательные требования к генерации:**

- Добавляются все разделы из `required_sections` (дефолтные или из проектных требований)
- Запрещённые слова из `forbidden_words` автоматически фильтруются (скилл не генерирует их)
- Все единицы измерения указаны явно
- Для каждой инструкции есть рабочий пример

---

### Шаг 5: Создание Antora-конфигурации

**Что делает скилл:**

1. Для каждого компонента создаёт `antora.yml`:

```yaml
name: {component-name}
title: {Human-readable title}
version: {version}
nav:
  - modules/ROOT/nav.adoc
```

2. Для каждого компонента создаёт `playbook-{component}.yml`:

```yaml
site:
  title: {Title} Documentation
  url: https://example.com/docs/{component}
content:
  sources:
    - url: ./
      branches: HEAD
      start_path: docs/antora/{component}
output:
  dir: ./build/site/{component}
```

3. Учитывает `build_tool` и `output_format` из проектных требований (если они там указаны)

---

### Шаг 6: Добавление cross-references

**Что делает скилл:**

1. **Внутри компонента:** добавляет ссылки вида `xref:page.adoc`

2. **Между компонентами:** добавляет ссылки вида `xref:{component}::page.adoc`

3. Автоматически определяет, какие ссылки нужны, на основе анализа артефактов и их зависимостей

4. Предлагает пользователю утвердить список cross-references перед финальной генерацией

---

### Шаг 7: Генерация вспомогательных файлов

**Что делает скилл:**

1. Создаёт `update.md` — инструкцию по обновлению документации при изменении артефактов:
   - Какие команды запускать в CI
   - Как пересобрать сайты
   - Как проверить актуальность

2. Создаёт `review-checklist.md` — чеклист для редактора:

```markdown
# Контрольный список проверки документации

## Базовые проверки

- [ ] Все единицы измерения указаны явно (ms, bytes, mb)?
- [ ] Нет запрещённых слов: легко, просто, тривиально, очевидно?
- [ ] Каждый пример проверен на «чистой машине» (без предварительной настройки)?
- [ ] Cross-reference между компонентами работают и ведут на правильные сайты?
- [ ] Все внешние ссылки заменены на локальные (или помечены как опциональные)?
- [ ] Для air-gapped поставки — нет CDN, все ресурсы в репозитории?
- [ ] Активный залог использован вместо пассивного?
- [ ] Нет нерасшифрованных аббревиатур и латинизмов?
- [ ] Предупреждения о недокументированном поведении явно выделены?
- [ ] Навигация (nav.adoc) полная и логичная?

## Дополнительные проверки (из проектных требований)

(скилл добавляет сюда пункты, извлечённые из артефакта требований)
```

---

### Шаг 8: Запрос на доработку и завершение

**Что делает скилл:**

1. Если проектные требования указывают на обязательное наличие определённых артефактов (например, «каждый API-метод должен быть описан в отдельном файле»), а скилл их не нашёл — явно перечисляет недостающее и запрашивает у пользователя

2. Выводит итоговую структуру сгенерированных файлов

3. Сообщает пользователю, куда сохранены:
   - AsciiDoc-файлы
   - Antora-конфигурации
   - `update.md`
   - `review-checklist.md`

4. Указывает, какие команды нужно запустить для сборки документации через Antora

---

## Обработка конфликтов

Если в проектных требованиях указано нечто, что противоречит дефолтной логике скилла, скилл:

1. **Применяет требования** (они приоритетнее, см. таблицу «Приоритет параметров»)

2. Выводит предупреждение в лог генерации:

> *«Внимание: проектные требования отключают версионирование (versioning: false). Дефолтное значение true проигнорировано.»*

## Примечания

- Скилл **не генерирует код** приложения, только документацию
- Скилл **не изменяет артефакты** в `artifacts_path`
- Если артефакты меняются — пользователь вызывает скилл повторно
- Стилистические правила являются **жёсткими** (удаление «ридмитита» — обязательное требование)

## Cleanup

После завершения генерации:
1. **Валидация всех созданных YAML-файлов.** Запустите `yamllint -c .yamllint .` из корня проекта. Если найдены ошибки (не предупреждения) — исправьте их перед завершением. Это относится к: `antora.yml`, `playbook-*.yml` и любым другим YAML-файлам, созданным скиллом.
2. Убедитесь, что все YAML-файлы имеют корректную структуру: правильная индентация, перевод строки в конце файла, нет лишних пустых строк.
