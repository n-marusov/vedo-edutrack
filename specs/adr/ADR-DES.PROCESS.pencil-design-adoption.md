# ADR-DES.PROCESS.pencil-design-adoption

**Статус:** ПРИНЯТО
**Дата:** 2026-08-02
**Контекст:** Инструмент и процесс дизайна фронтенда (M0.1, T5 — конвенции репозиторной структуры фронтенда)

Фронтенд-стек зафиксирован в `ADR-DES.STACK.language-vs-vs` и `ADR-DES.STACK.framework-vs-vs` (оба ПРИНЯТО, T3): **React + TypeScript**, визуализация — React Flow (конструктор маршрутов F4.3) + Cytoscape.js (карта знаний F4.1, canvas), типизированный клиент — `openapi-typescript`, i18n — react-i18next, состояние — Zustand, тесты — React Testing Library + Playwright. Продукт — тяжёлая SPA-визуализация, UX-ядро (F4). Команда работает в режиме вайбкодинга (AI-assisted разработка) со стратегией «компенсация тестированием и документацией». Внутренняя структура фронтенда — Clean Architecture (`ADR-DES.INFRA.clean-architecture-adoption`): Domain/Application/Interface Adapters/Frameworks, бизнес-правила не живут в компонентах.

Дизайн-процесс до сих пор не зафиксирован: непонятно, где живут дизайн-артефакты (макеты экранов, дизайн-токены), как они версионируются, как ИИ-ассистенты получают структуру UI (скриншоты — плохой источник для генерации кода), и как дизайн синхронизируется с кодом без классического «handoff»-трения (Figma → разработчик: потеря точности, 15–20% таймлайна на передачу).

**Ключевые драйверы:**
- **Вайбкодинг UI**: ИИ должен читать и писать дизайн структурно (узлы, токены, layout), а не угадывать по скриншотам; требуются read+write инструменты канваса через MCP.
- **Дизайн как код**: артефакты дизайна обязаны версионироваться в Git вместе с кодом (diff, branch, merge, review) — единый контур поставки (Community/Enterprise, `REQ-NFR-infra.compliance.client-server-web-app`).
- **Дизайн-токены ↔ CSS**: темы (light/dark), i18n-готовность и WCAG-итерации должны обновляться через переменные без переписывания бизнес-правил (`REQ-NFR-ops.compliance.i18n-readiness`, `REQ-NFR-ui.compliance.wcag-level`).
- **Границы Clean Architecture**: дизайн-артефакты — периферия (Interface Adapters/Frameworks); доменные инварианты живут только в коде Domain/Application, `.pen`-файлы не являются источником бизнес-правил.
- **Онбординг и bus-factor**: единый словарь и воспроизводимый процесс дизайна для команды 2–10 человек (`REQ-NFR-process.dev.developer-documentation`).
- **Стек уже выбран** (T3): инструмент дизайна обязан генерировать код под React + TypeScript и синхронизировать токены с CSS без привязки к конкретному фреймворку стилей.

**Требование-источник:**
- `REQ-NFR-infra.compliance.client-server-web-app` (веб-приложение, клиент-сервер)
- `REQ-NFR-process.dev.engineering-gates` (архитектурные тесты и линтеры в CI — дизайн-артефакты не обходят гейты)
- `REQ-NFR-process.dev.developer-documentation` (единый словарь, онбординг, bus-factor ≥ 2)
- `REQ-NFR-ops.compliance.i18n-readiness` (RU+EN, ICU — строки на периферии)
- `REQ-NFR-ui.compliance.wcag-level` (WCAG 2.1 AA — UI заменяем итерациями)
- `REQ-NFR-process.dev.test-coverage` (покрытие ядра в изоляции — дизайн не должен тянуть зависимости в тесты ядра)

**Решение:**

Принять **Pencil (pen.dev)** как инструмент дизайна фронтенда и зафиксировать процесс «дизайн как код»:

1. **Артефакты дизайна — `.pen`-файлы в репозитории** рядом с кодом (`design/` на уровне репозитория, рядом с `src/` фронтенда). `.pen` — открытый JSON-формат: версионируется в Git (текстовые диффы), читается людьми и ИИ.
2. **MCP-интеграция**: локальный MCP-сервер pen.dev даёт ИИ-ассистентам (Claude Code CLI — основной инструмент команды) read+write доступ к канвасу: создание экранов, компонентов, токенов, экспорт структуры для генерации кода.
3. **Дизайн-токены — источник для CSS**: переменные pen.dev (цвета, типографика, отступы, радиусы; темы light/dark) синхронизируются с CSS-переменными фронтенда двунаправленно (pen.dev → CSS, CSS → pen.dev).
4. **Генерация кода — только под принятый стек**: React + TypeScript + Tailwind CSS (T3); компоненты из дизайна генерируются как React-компоненты с типизированными пропсами; спецификация библиотек иконок (Lucide/Feather/Phosphor — встроенные в pen.dev) — в промптах генерации.
5. **Позиция в Clean Architecture**: `.pen`-артефакты и дизайн-токены — периферия (Interface Adapters/Frameworks, слой UI-компонентов). Бизнес-правила (Domain/Application) в дизайн-файлы не попадают; дизайн не заменяет архитектурные тесты и unit-тесты ядра.
6. **Процесс**: design-first для новых фич (дизайн → генерация кода → рефакторинг → обратная синхронизация), import-code-to-design для существующих компонентов (двусторонний sync-цикл).

**Уточнение стека (фронтенд, согласно T3):**

| Слой | Технология (ПРИНЯТО в T3) | Роль в дизайн-процессе Pencil |
|------|----------------------------|-------------------------------|
| Язык | **TypeScript** | Генерация кода из `.pen` — типизированные React-компоненты |
| UI-фреймворк | **React 18+** | Целевой формат генерируемых компонентов |
| Визуализация | **React Flow** (конструктор), **Cytoscape.js** (карта знаний) | Специфические компоненты — не генерируются из дизайна, интегрируются как внешние библиотеки; дизайн определяет их обёртки (адаптеры) |
| API-клиент | **openapi-typescript** (из OpenAPI-спеки) | Типы DTO — из спеки, не из дизайна (дизайн не источник данных) |
| Состояние | **Zustand** | Слой Application; дизайн-файлы не описывают состояние |
| i18n | **react-i18next** (ICU) | Строки — в i18n-ресурсах, не в дизайне; дизайн определяет раскладку/контейнеры |
| Стилизация | **Tailwind CSS** (принят, `ADR-DES.STACK.framework-vs-vs`) + **CSS-переменные (дизайн-токены)** — токены в `@theme`, темы light/dark | Синхронизация переменных pen.dev ↔ CSS (`@theme`); генерация Tailwind-классов из дизайна |
| Тесты UI | **React Testing Library + Playwright** | Генерируемые компоненты обязаны проходить те же гейты; дизайн не освобождает от тестов |

Pencil-специфичные артефакты: `*.pen` (экраны/компоненты), `*.lib.pen` (дизайн-библиотеки, e.g. брендовый UI-kit EduTrack), импорт Figma — только как входная миграция существующих макетов, не как постоянный контур.

**Рассмотренные альтернативы:**

| Альтернатива | Оценка | Причина отклонения |
|--------------|--------|--------------------|
| **Figma / Sketch (классический handoff)** | ❌ | Внешний инструмент: дизайн-файлы вне репозитория (нет версионирования как кода), ИИ получает скриншоты, а не структуру; трение передачи «дизайн → код» (потери точности, 15–20% таймлайна); MCP-запись канваса отсутствует/ограничена. Figma-импорт в pen.dev остаётся разовым переходом |
| **Screenshot-to-code без дизайн-файла** | ❌ | Скриншот — визуальная ссылка, из него нельзя восстановить иерархию, отступы и токены с уверенностью (снижение качества генерации); нет единого источника правды, нет итераций дизайна |
| **Code-first (дизайн сразу в коде, без дизайн-инструмента)** | ⚠️ | Быстро для простых экранов, но теряется визуальное исследование и «макет до кода» для UX-ядра (F4 — графы, дашборды, конструктор); хуже для вайбкодинга (ИИ без структурного канваса); оставлен как частный случай для тривиальных фич |
| **Только UI-kit из кода (MUI и т.п.)** | ⚠️ | Компонентная база полезна, но не закрывает дизайн-систему: токены, темы, макеты экранов, варианты состояний — нужен инструмент уровня дизайна; UI-kit остаётся частью процесса (как библиотека компонентов), не заменой |

**Последствия:**

*Положительные:*
- **Дизайн и код в одном репозитории**: единый контур поставки, диффы, branch/merge, review — исчезает ручной «handoff».
- **Вайбкодинг UI**: ИИ читает и пишет структурированный дизайн (MCP), генерация React-компонентов с высокой точностью (структура, а не пиксели).
- **Токены ↔ CSS**: темы light/dark, WCAG-итерации и i18n-раскладки меняются в одном месте; замена UI-фреймворка не трогает бизнес-правила (синергия с Clean Architecture).
- **Открытый формат**: `.pen` — документированный JSON (TypeScript-схема в доках pen.dev), не бинарный проприетарный формат; экспорт PNG/JPEG/PDF и импорт Figma снижают риск блокировки.
- **Воспроизводимый процесс**: единый словарь (экраны, компоненты, токены) для команды и ИИ — дешевле онбординг, выше bus-factor.

*Отрицательные и смягчение:*
- **Молодой инструмент**: нет автосейва, возможны breaking changes формата (версия `2.14`, «live documentation») → дисциплина сохранения + частые Git-коммиты; формат версионируется в схеме; при необходимости — экспорт и миграция.
- **Зависимость от вендора (MCP-сервер, расширение IDE)** → MCP-сервер локальный (без облака для операций дизайна), дизайн-файлы в нашем репозитории; смена инструмента не теряет артефакты (JSON открыт).
- **Известные проблемы**: Codex `config.toml` (бэкап конфига), Cursor Pro для части фич, Linux Wayland → документировать в `docs/` (troubleshooting) и в справочнике `.ai-factory/references/pencil-dev.md`.
- **Риск протечь бизнес-правила в дизайн** (нарушение Clean Architecture) → гейты: архитектурные тесты + линтеры в CI (`engineering-gates`), чек-лист ревью; `.pen`-файлы исключены из источников правил домена.
- **Дисциплина токенов** (литералы вместо переменных в дизайне) → конвенции ревью + арх-тесты на уровне стилей (проверка использования переменных), см. ADR репозиторной структуры (T5).
