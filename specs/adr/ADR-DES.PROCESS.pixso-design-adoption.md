# ADR-DES.PROCESS.pixso-design-adoption

**Статус:** ПРИНЯТО
**Дата:** 2026-08-04
**Контекст:** Инструмент и процесс дизайна фронтенда (M0.1, T5 — конвенции репозиторной структуры фронтенда). Замена Pencil (pen.dev) на Pixso.

Фронтенд-стек зафиксирован в `ADR-DES.STACK.language-vs-vs` и `ADR-DES.STACK.framework-vs-vs` (оба ПРИНЯТО, T3): **React + TypeScript**, визуализация — React Flow (конструктор маршрутов F4.3) + Cytoscape.js (карта знаний F4.1, canvas), типизированный клиент — `openapi-typescript`, i18n — react-i18next, состояние — Zustand, тесты — React Testing Library + Playwright. Продукт — тяжёлая SPA-визуализация, UX-ядро (F4). Команда работает в режиме вайбкодинга (AI-assisted разработка) со стратегией «компенсация тестированием и документацией». Внутренняя структура фронтенда — Clean Architecture (`ADR-DES.INFRA.clean-architecture-adoption`): Domain/Application/Interface Adapters/Frameworks, бизнес-правила не живут в компонентах.

Дизайн-процесс до сих пор не зафиксирован: непонятно, где живут дизайн-артефакты (макеты экранов, дизайн-токены), как они версионируются, как ИИ-ассистенты получают структуру UI (скриншоты — плохой источник для генерации кода), и как дизайн синхронизируется с кодом без классического «handoff»-трения (Figma → разработчик: потеря точности, 15–20% таймлайна на передачу).

Первоначально был принят Pencil (pen.dev) как инструмент «дизайн как код» с `.pen`-файлами в репозитории. После ознакомления с ограничениями Pencil (отсутствие автосейва, сырая экосистема, Wayland-проблемы на Linux, формат «живой» — возможны breaking changes, необходимость IDE-расширения) принято решение мигрировать на **Pixso** — зрелый облачный инструмент дизайна с MCP-интеграцией, не уступающий Figma по возможностям коллаборации и предоставляющий AI-агентам read+write доступ к канвасу через MCP.

**Ключевые драйверы:**
- **Вайбкодинг UI**: ИИ должен читать и писать дизайн структурно (узлы, токены, layout), а не угадывать по скриншотам; требуются read+write инструменты канваса через MCP — Pixso предоставляет такой API.
- **Дизайн как код**: дизайн-артефакты версионируются и синхронизируются с кодом; Pixso SDK для экспорта/импорта и MCP-инструменты покрывают этот контур.
- **Дизайн-токены ↔ CSS**: темы (light/dark), i18n-готовность и WCAG-итерации должны обновляться через переменные без переписывания бизнес-правил (`REQ-NFR-ops.compliance.i18n-readiness`, `REQ-NFR-ui.compliance.wcag-level`).
- **Границы Clean Architecture**: дизайн-артефакты — периферия (Interface Adapters/Frameworks); доменные инварианты живут только в коде Domain/Application, дизайн-файлы не являются источником бизнес-правил.
- **Онбординг и bus-factor**: единый словарь и воспроизводимый процесс дизайна для команды 2–10 человек (`REQ-NFR-process.dev.developer-documentation`).
- **Облачная коллаборация**: команда работает удалённо — нужен общий доступ к макетам в реальном времени без настройки репозитория для каждого дизайнера.
- **Стек уже выбран** (T3): инструмент дизайна обязан генерировать код под React + TypeScript и синхронизировать токены с CSS.

**Требование-источник:**
- `REQ-NFR-infra.compliance.client-server-web-app` (веб-приложение, клиент-сервер)
- `REQ-NFR-process.dev.engineering-gates` (архитектурные тесты и линтеры в CI — дизайн-артефакты не обходят гейты)
- `REQ-NFR-process.dev.developer-documentation` (единый словарь, онбординг, bus-factor ≥ 2)
- `REQ-NFR-ops.compliance.i18n-readiness` (RU+EN, ICU — строки на периферии)
- `REQ-NFR-ui.compliance.wcag-level` (WCAG 2.1 AA — UI заменяем итерациями)
- `REQ-NFR-process.dev.test-coverage` (покрытие ядра в изоляции — дизайн не должен тянуть зависимости в тесты ядра)

**Решение:**

Принять **Pixso** как инструмент дизайна фронтенда и зафиксировать соответствующий процесс:

1. **Дизайн-артефакты в Pixso**: экраны, компоненты и дизайн-токены создаются в облачном редакторе Pixso. Дизайн-система (UI-kit, токены, темы light/dark) ведётся в выделенном Pixso-файле библиотеки.
2. **MCP-интеграция**: Pixso MCP-сервер предоставляет ИИ-ассистентам read+write доступ к канвасу: создание/редактирование элементов, чтение структуры, управление токенами, экспорт для генерации кода.
3. **Дизайн-токены — источник для CSS**: переменные Pixso (цвета, типографика, отступы, радиусы; темы light/dark) экспортируются в CSS-переменные фронтенда. Синхронизация — через MCP-инструменты (read_variables / write_variables) или экспорт токенов в CSS.
4. **Генерация кода — только под принятый стек**: React + TypeScript + Tailwind CSS (T3); компоненты из дизайна генерируются как React-компоненты через design_to_code / export_html с Tailwind-форматом; типизированные пропсы — из структуры компонентов Pixso.
5. **Позиция в Clean Architecture**: Pixso-артефакты и дизайн-токены — периферия (Interface Adapters/Frameworks, слой UI-компонентов). Бизнес-правила (Domain/Application) в дизайн-файлы не попадают; дизайн не заменяет архитектурные тесты и unit-тесты ядра.
6. **Процесс**: design-first для новых фич (дизайн → генерация кода → рефакторинг → обратная синхронизация), code-to-design для существующих компонентов (импорт HTML/CSS в Pixso через code_to_design / экспорт макетов).

**Уточнение стека (фронтенд, согласно T3):**

| Слой | Технология (ПРИНЯТО в T3) | Роль в дизайн-процессе Pixso |
|------|----------------------------|------------------------------|
| Язык | **TypeScript** | Генерация кода из структуры Pixso — типизированные React-компоненты |
| UI-фреймворк | **React 18+** | Целевой формат генерируемых компонентов |
| Визуализация | **React Flow** (конструктор), **Cytoscape.js** (карта знаний) | Специфические компоненты — не генерируются из дизайна, интегрируются как внешние библиотеки; дизайн определяет их обёртки (адаптеры) |
| API-клиент | **openapi-typescript** (из OpenAPI-спеки) | Типы DTO — из спеки, не из дизайна (дизайн не источник данных) |
| Состояние | **Zustand** | Слой Application; дизайн не описывает состояние |
| i18n | **react-i18next** (ICU) | Строки — в i18n-ресурсах, не в дизайне; дизайн определяет раскладку/контейнеры |
| Стилизация | **Tailwind CSS** (принят, `ADR-DES.STACK.framework-vs-vs`) + **CSS-переменные (дизайн-токены)** — токены в `@theme`, темы light/dark | Синхронизация переменных Pixso ↔ CSS (`@theme`); генерация Tailwind-классов из дизайна |
| Тесты UI | **React Testing Library + Playwright** | Генерируемые компоненты обязаны проходить те же гейты; дизайн не освобождает от тестов |

Артефакты Pixso: файлы дизайна в облаке (с доступом по ссылкам), экспорт дизайн-токенов в CSS, генерация React-компонентов через MCP (design_to_code). Figma-импорт — только как входная миграция существующих макетов, не как постоянный контур.

**Рассмотренные альтернативы:**

| Альтернатива | Оценка | Причина отклонения |
|--------------|--------|--------------------|
| **Figma (классический handoff)** | ⚠️ | Зрелый инструмент, огромная экосистема, но: MCP-запись канваса отсутствует (только чтение через REST API, нет write), ИИ получает скриншоты/JSON через плагины, а не нативный MCP; трение «дизайн → код» выше, чем у Pixso с нативным MCP |
| **Pencil (pen.dev)** | ⚠️ | «Дизайн как код» с `.pen`-файлами в репозитории — хорошая идея, но: нет автосейва, сырая экосистема, проблемы с Linux Wayland, формат «живой» с потенциальными breaking changes; отсутствие облачной коллаборации. Заменён на Pixso, который предоставляет зрелый облачный сервис + MCP |
| **Screenshot-to-code без дизайн-файла** | ❌ | Скриншот — визуальная ссылка, из него нельзя восстановить иерархию, отступы и токены с уверенностью (снижение качества генерации); нет единого источника правды, нет итераций дизайна |
| **Code-first (дизайн сразу в коде, без дизайн-инструмента)** | ⚠️ | Быстро для простых экранов, но теряется визуальное исследование и «макет до кода» для UX-ядра (F4 — графы, дашборды, конструктор); хуже для вайбкодинга (ИИ без структурного канваса); оставлен как частный случай для тривиальных фич |
| **Только UI-kit из кода (MUI и т.п.)** | ⚠️ | Компонентная база полезна, но не закрывает дизайн-систему: токены, темы, макеты экранов, варианты состояний — нужен инструмент уровня дизайна; UI-kit остаётся частью процесса (как библиотека компонентов), не заменой |

**Последствия:**

*Положительные:*
- **Облачная коллаборация**: дизайнеры и разработчики работают в одном пространстве, изменения видны в реальном времени.
- **Вайбкодинг UI**: ИИ читает и пишет структурированный дизайн через MCP (query_nodes, apply_design, design_to_code), генерация React-компонентов с высокой точностью.
- **Токены ↔ CSS**: темы light/dark, WCAG-итерации и i18n-раскладки меняются в одном месте; замена UI-фреймворка не трогает бизнес-правила (синергия с Clean Architecture).
- **Экспорт кода**: design_to_code / export_html с Tailwind-форматом — быстрый путь от макета к production-компоненту.
- **Воспроизводимый процесс**: единый словарь (экраны, компоненты, токены) для команды и ИИ — дешевле онбординг, выше bus-factor.

*Отрицательные и смягчение:*
- **Облачная зависимость**: дизайн-файлы не в репозитории, а в облаке Pixso → при недоступности сервиса работа с макетами невозможна. Смягчение: экспорт .pixso-файлов и токенов в репозиторий как снепшотов (периодический бэкап), Git LFS для бинарных артефактов дизайна при необходимости.
- **Зависимость от вендора (MCP-сервер, API)** → MCP-инструменты используем через локального провайдера; при смене инструмента экспорт макетов (PNG/PDF/SVG) и токенов (CSS) сохраняется.
- **Риск протечь бизнес-правила в дизайн** (нарушение Clean Architecture) → гейты: архитектурные тесты + линтеры в CI (`engineering-gates`), чек-лист ревью; Pixso-файлы не являются источником бизнес-правил.
- **Дисциплина токенов** (литералы вместо переменных в дизайне) → конвенции ревью + арх-тесты на уровне стилей (проверка использования переменных).
- **Версионирование дизайн-файлов** → Pixso поддерживает историю версий; при необходимости — снепшоты в Git.
