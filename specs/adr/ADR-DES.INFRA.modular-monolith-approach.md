# ADR-DES.INFRA.modular-monolith-approach

**Статус:** ПРИНЯТО
**Дата:** 2026-08-02
**Контекст:** Архитектурный стиль системы до выбора стека (M0.1)

Необходимо зафиксировать архитектурный стиль VEDO EduTrack перед выбором языка и фреймворка (T3). Предметная область декомпозирована на 10 ограниченных контекстов (`specs/ddd/context-map.md`): 3 core (`route-planning`, `execution-progress`, `gap-coverage`), 5 supporting (`plan-management`, `ontology-port`, `resources`, `practice-life`, `visualization`), 2 generic (`identity-access`, `integrations`). Продукт поставляется как веб-приложение с клиент-серверной архитектурой (`REQ-NFR-infra.compliance.client-server-web-app`).

**Ключевые драйверы решения:**
- Каскадные пересчёты (vision F1.6, §2.4): `ModuleMastered → RouteRecalculated → Resources/Stories → Plan` — цепочка вычислений, критичная к латентности.
- Три core-контекста связаны событийно-плотным циклом «маршрут → исполнение → лакуны»; разнесение их по сети прямо бьёт по p95 ≤ 200 мс (`REQ-NFR-api.performance.latency-p95`).
- Два контура развёртывания (Community SaaS / Enterprise on-prem, 152-ФЗ) с изоляцией (`REQ-NFR-infra.compliance.community-enterprise-isolation`).
- Малая команда (стартап), MVP-темп, RPO ≤ 1 ч / RTO ≤ 4 ч (`REQ-NFR-data.availability.backup-rpo`).
- **Простота развёртывания и обслуживания для сторонних заказчиков**: Enterprise-контур развёртывается on-premise / private cloud силами клиента (или с ограниченной поддержкой вендора) — один артефакт с минимумом внешних зависимостей радикально снижает стоимость установки, эксплуатации и поддержки (SLA Enterprise ≤ 1 ч, `REQ-NFR-ops.compliance.support-sla`).
- **Масштабируемость под B2B-нагрузку**: EdTech-платформа («Свой Вектор», persona CTO/CPO §3.1) подключает к сервису тысячи своих клиентов через REST API (F6.1) — сервис обязан выдерживать кратный рост запросов без деградации (`REQ-NFR-ops.performance.scalability`: 10× пик относительно базовых 1000 concurrent, stateless, автоскейлинг ≤ 5 мин; `REQ-NFR-api.performance.latency-p95`: p95 ≤ 200 мс).
- Детерминированное ядро (F1/F2) требует высокого качества тестов (`REQ-NFR-process.dev.test-coverage`); визуализация — read-heavy (F4).

**Требование-источник:**
- `REQ-NFR-api.performance.latency-p95` (p95 ≤ 200 мс при 1000 concurrent)
- `REQ-NFR-ops.performance.scalability` (горизонтальное масштабирование, stateless)
- `REQ-NFR-infra.compliance.community-enterprise-isolation` (изоляция контуров)
- `REQ-NFR-infra.compliance.client-server-web-app` (форма поставки: веб-приложение, клиент-сервер)
- `REQ-NFR-process.dev.test-coverage` (ядро F1/F2 ≥ 90% покрытия, mutation testing)
- `REQ-NFR-data.availability.backup-rpo` (RPO ≤ 1 ч, RTO ≤ 4 ч)
- `REQ-NFR-ops.compliance.support-sla` (тиры поддержки: Enterprise ≤ 1 ч — простая система дешевле обслуживать)
- `REQ-NFR-security.compliance.owasp-application-security` (OWASP Top 10, JWT RS256)

**Решение:**

Принять **модульный монолит (modular monolith)** как архитектурный стиль системы:

- **Один разворачиваемый артефакт** (один деплой/контейнер сервера) на оба контура; контуры различаются конфигурацией, тирами и изоляцией данных (схемы/tenant), а не структурой приложения.
- **Модуль = ограниченный контекст**: каждый из 10 контекстов — отдельный гексагональный модуль (ports & adapters), домен внутри, инфраструктура снаружи. Модули не импортируют друг друга напрямую.
- **Событийная связность in-process**: каскады (`RouteRecalculated`, `ModuleMastered`, `PlanDeviationDetected`, …) доставляются асинхронной in-process шиной внутри процесса — без сетевых вызовов, с сохранением гарантий порядка для одного агрегата.
- **Outbox для внешних интеграций**: события, уходящие во внешние webhook/LMS/MCP, проходят через outbox-паттерн с идемпотентной доставкой (`REQ-FR-api.webhooks.idempotency`).
- **Read-модели для визуализации**: `visualization` — тонкие read-only проекции над материализованными read-моделями (CQRS-light), не прямые запросы в ядро.
- **Кэш и очередь за портами**: кэширование (подграф онтологии, read-модели) и очередь (outbox) — адаптеры за гексагональными портами. На MVP: in-memory кэш Go-процесса (подграф иммутабелен по `ontologyVersion` — распределённый кэш не нужен) + outbox-таблица в PostgreSQL. Redis (или иной брокер) — пост-MVP адаптер по триггеру (кросс-нодовый WebSocket/SSE fan-out, распределённый rate limiting при 10× нагрузке, тяжёлый outbox-трафик) — замена без изменения ядра.
- **Ядро без инфраструктуры**: детерминированные алгоритмы (маршруты, лакуны, покрытие) — чистые функции, зависящие только от портов (онтология, позиция).
- **Слоты эволюции**: гексагональные границы позволяют вынести любой контекст (например, `integrations` или `visualization`) в отдельный сервис без переписывания ядра, если возникнет потребность в независимом масштабировании/деплое.

**Рассмотренные альтернативы:**

| Альтернатива | Оценка | Причина отклонения |
|--------------|--------|--------------------|
| **Микросервисы** (контекст = сервис) | ❌ | Каскад из 3 core-контекстов через сеть подъедает бюджет p95 ≤ 200 мс; распределённые транзакции/саги; N контейнеров на on-prem Enterprise (дорого для сторонних заказчиков: оркестратор, N сервисов в поддержке); операционный ад для малой команды; сложнее RPO/RTO и тестирование ядра; при B2B-нагрузке (тысячи клиентов платформы) выигрыша нет — узкое место (Hub API, read-нагрузка) решается репликами + кэшем, а не разбиением ядра |
| **Сервис-ориентированная архитектура** (укрупнённые сервисы по 2–3 контекста) | ⚠️ | Промежуточный вариант: разбивает ядро (core-контексты в разных сервисах) без выигрыша в масштабировании; сложность сети без пользы на MVP-нагрузке |
| **Плоский (слоистый) монолит** | ⚠️ | Не уважает границы bounded contexts: риск «big ball of mud», нарушение инвариантов (маршрут — функция, траектория всегда видна); без событийной шины каскады становятся жёсткими вызовами |
| **Событийно-ориентированная архитектура** (как самостоятельный стиль) | ⚠️ | Не альтернатива, а механизм внутри: принята как in-process шина + outbox (см. Решение); standalone-EDA без ядра не отвечает на вопрос «где живёт домен» |

**Последствия:**

*Положительные:*
- Каскадные пересчёты исполняются in-process — мгновенно, без сетевых задержек; p95 ≤ 200 мс достижимо (3–5 реплик за балансировщиком закрывают 1000 concurrent).
- Enterprise on-prem: один артефакт, простая изоляция контуров (схемы/конфигурация), простой бэкап/восстановление (RPO/RTO).
- **Сторонние заказчики**: установка Enterprise = развёртывание одного контейнера/артефакта + PostgreSQL (Redis не требуется на MVP — один компонент хранения); обслуживание не требует оркестратора (Kubernetes не обязателен на MVP); стоимость поддержки ниже — меньше компонентов для диагностики (SLA Enterprise ≤ 1 ч).
- **Тысячи клиентов EdTech-платформы**: для монолита нагрузка масштабируется целиком-артефактно — stateless-реплики за балансировщиком (автоскейлинг добавляет ноду ≤ 5 мин при 10× пике), каждый контекст масштабируется вместе с артефактом. Узкое место в этом сценарии — не ядро, а внешний VEDO Hub (SPARQL/подграф): оно снимается копированием подграфа (F0.2), in-memory кэшем подграфа (иммутабелен по `ontologyVersion`) и circuit breaker (`REQ-NFR-api.availability.hub-dependency-sla`); read-нагрузка визуализации уходит на read-модели (проекции в PostgreSQL); rate limiting по API-ключу защищает сервис от перегрузки отдельной платформой (`REQ-NFR-security.compliance.owasp-application-security`).
- Тестирование ядра: unit/integration без тестовых двойников сети — покрытие F1/F2 ≥ 90% реалистично.
- Малая команда: один репозиторий, один деплой, быстрые итерации MVP.
- Границы контекстов сохранены → путь к микросервисам (если понадобится) не переписывание, а вынос модуля.

*Отрицательные и смягчение:*
- Нет независимого масштабирования/деплоя отдельных контекстов → смягчение: для B2B-нагрузки (тысячи клиентов платформы) это не требуется — stateless-реплики всего артефакта + автоскейлинг закрывают 10× пик; read-модели (проекции в PostgreSQL) + in-memory кэш снимают read-нагрузку визуализации; слоты эволюции позволяют вынести контекст (например, `integrations`), если появится потребность в отдельном деплое.
- Требует дисциплины границ модулей (запрет прямых импортов между контекстами) → смягчение: архитектурные тесты/линтеры (dependency rules, arch-unit эквивалент) в CI (`REQ-NFR-process.dev.engineering-gates`).
- Один процесс = единая точка отказа → смягчение: stateless реплики за балансировщиком, multi-AZ (`REQ-NFR-infra.availability.multi-az-geo-dr`), готовность к горизонтальному масштабированию (`REQ-NFR-ops.performance.scalability`).
- LLM-модуль (генерация с валидацией) должен оставаться изолированным адаптером, чтобы не загрязнять детерминированное ядро → смягчение: гексагональный модуль `integrations`/отдельный адаптер LLM с generate-and-validate.
