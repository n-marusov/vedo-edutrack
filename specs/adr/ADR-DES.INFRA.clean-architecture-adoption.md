# ADR-DES.INFRA.clean-architecture-adoption

**Статус:** ПРИНЯТО
**Дата:** 2026-08-02
**Контекст:** Внутренняя структура кода бэкенда и фронтенда до выбора стека (M0.1)

Архитектурный стиль системы зафиксирован в `ADR-DES.INFRA.modular-monolith-approach`: модульный монолит, где каждый из 10 ограниченных контекстов — отдельный модуль, организованный по Clean Architecture (ports & adapters на границах). Стиль определяет **внешнюю** структуру (один артефакт, модули, события, outbox), но не задаёт **внутреннюю** организацию кода внутри модуля и не покрывает фронтенд. Настоящий ADR фиксирует слоистую структуру ядра (Clean Architecture) на обоих концах клиент-серверного приложения (`REQ-NFR-infra.compliance.client-server-web-app`).

**Ключевые драйверы решения:**
- **Детерминированное ядро с высокими требованиями к тестированию** (F1/F2): маршрут — функция, диагностика лакун, покрытие FGOS. Требуется покрытие ядра ≥ 90% + mutation testing (`REQ-NFR-process.dev.test-coverage`) — бизнес-правила обязаны тестироваться без UI, БД и сети.
- **Фронтенд несёт доменное поведение**, а не только рендеринг: plan-vs-actual, индикация лакун, конструктор маршрута, дашборды (F2/F4) — логика не может жить только в компонентах.
- **Внешняя граница VEDO Hub** (REST API, MCP, SPARQL): форматы данных онтологии не должны протекать в бизнес-правила; смена контракта Hub не должна ломать ядро (`REQ-NFR-api.availability.hub-dependency-sla`).
- **Два контура развёртывания** (Community/Enterprise) разделяют один API-контракт (`REQ-NFR-infra.compliance.community-enterprise-isolation`) — домен обязан быть контуро-агностичным.
- **Стек — TBD**: решение уровня `DES` и обязано выдержать любой кандидат стека (язык: TypeScript/Go/Python/Java; фреймворк бэкенда: NestJS/FastAPI/Spring; фронтенд: React/Vue) без переписывания ядра.
- **p95 ≤ 200 мс** (`REQ-NFR-api.performance.latency-p95`): тонкие адаптеры и чистое ядро без инфраструктурных зависимостей защищают бюджет латентности.
- **i18n-готовность (RU+EN) и WCAG 2.1 AA** (`REQ-NFR-ops.compliance.i18n-readiness`, `REQ-NFR-ui.compliance.wcag-level`): UI должен заменяться итерациями без правок бизнес-правил.
- **Длительно живущее бизнес-приложение со сложным поведением** (109 требований, 10 контекстов, 47 US) — именно тот случай, для которого Clean Architecture уместна (критерий Палермо), в отличие от небольших сайтов.
- **Единый словарь на оба конца**: симметричная структура и стратегия тестов упрощают онбординг и снижают bus-factor (`REQ-NFR-process.dev.developer-documentation`).

**Требование-источник:**
- `REQ-NFR-process.dev.test-coverage` (ядро F1/F2 ≥ 90%, mutation testing)
- `REQ-NFR-process.dev.engineering-gates` (архитектурные тесты и линтеры в CI)
- `REQ-NFR-process.dev.code-complexity` (CC ≤ 10)
- `REQ-NFR-api.performance.latency-p95` (p95 ≤ 200 мс при 1000 concurrent)
- `REQ-NFR-api.availability.hub-dependency-sla` (граница VEDO Hub: contract tests, circuit breaker)
- `REQ-NFR-infra.compliance.client-server-web-app` (форма поставки: веб-приложение, клиент-сервер)
- `REQ-NFR-infra.compliance.community-enterprise-isolation` (изоляция контуров)
- `REQ-NFR-security.compliance.owasp-application-security` (OWASP Top 10, JWT RS256 — обработка в адаптерах)
- `REQ-NFR-ui.compliance.wcag-level` (WCAG 2.1 AA — UI заменяем без правок ядра)
- `REQ-NFR-ops.compliance.i18n-readiness` (RU+EN, ICU — строки и форматирование на периферии)

**Решение:**

Принять **Clean Architecture (Robert C. Martin)** как способ внутренней организации кода на бэкенде и фронтенде — дополнение к модульному монолиту (модуль = набор чистых кругов).

**Бэкенд (внутри каждого bounded-context модуля):**

| Круг (изнутри наружу) | Ответственность | Типичное содержимое |
|---|---|---|
| **Domain** | Предприятие-широкие и контекстные бизнес-правила, инварианты | Сущности, value objects, доменные сервисы, доменные события |
| **Application** | Прикладные сценарии (use cases), оркестрация; порты (интерфейсы) принадлежат этому кругу | Use case'ы, input/output ports, DTO |
| **Adapters** | Преобразование данных между внутренними форматами и внешними | REST-контроллеры, presenters, репозитории, клиенты VEDO Hub/SPARQL, мапперы, обработка auth/security |
| **Frameworks & Drivers** | Клей-код к внешнему миру | Фреймворк, БД, внешние сервисы, очередь |

**Фронтенд (зеркально):**

| Круг (изнутри наружу) | Ответственность | Типичное содержимое |
|---|---|---|
| **Domain** | Модели предметной области, инварианты, общие с бэкендом правила (статусы, допущения) | Доменные модели, типы, чистые функции |
| **Application** | Use cases интерфейса: загрузка маршрута, отслеживание плана, отображение лакун; состояние = слой use cases | Сторы/состояние, use case-сервисы, порты |
| **Interface Adapters** | Преобразование между форматами UI и use cases | View models, state-адаптеры, API-клиент, маппинг DTO |
| **Frameworks** | Внешний круг | UI-компоненты, роутер, фреймворк, браузер |

**Общие правила (обязательны на обоих концах):**
1. **Dependency Rule**: исходные зависимости направлены только внутрь; внутренний круг не знает имён (функций, классов, типов) внешних кругов.
2. **DIP на границах**: порты принадлежат внутренним кругам, реализации — внешним; динамический полиморфизм разворачивает зависимости против потока управления; composition root — на входе приложения.
3. **Через границы — простые DTO**: никогда сырые payload'ы VEDO Hub, строки БД, entity-объекты ORM; данные передаются в форме, удобной внутреннему кругу.
4. **Фреймворк — инструмент на периферии**: веб-фреймворк, БД, UI-фреймворк — детали; ядро от них не зависит.
5. **Доменный код фронтенда не живёт в компонентах**: компоненты — самый внешний круг; бизнес-правила — в Domain/Application, иначе недостижимо тестирование ядра.
6. **Тестирование**: unit-тесты Domain/Application в изоляции (без UI/БД/сети); integration-тесты адаптеров с реальными зависимостями; архитектурные тесты (dependency rules) и линтеры — в CI (`REQ-NFR-process.dev.engineering-gates`).
7. **Уровень `DES`, стек-независимо**: решение применяется к любому кандидату стека и не откладывается до выбора языка/фреймворка (в отличие от ADR `DES.STACK.*`).

**Рассмотренные альтернативы:**

| Альтернатива | Оценка | Причина отклонения |
|--------------|--------|--------------------|
| **Традиционный N-layer (UI/BLL/DAL)** | ❌ | Транзитивная связанность: BLL зависит от DAL; бизнес-логика привязана к деталям доступа к данным; тестирование требует тестовой БД — конфликт с `test-coverage`; типовой источник «big ball of mud» |
| **Только Ports-and-Adapters** | ⚠️ | Совместима и уже принята на уровне модулей монолита (адаптеры на границах), но не задаёт явную слоистую структуру внутри ядра (где живёт политика vs механика) и не покрывает фронтенд; Clean Architecture фиксирует структуру ядра явно |
| **Onion Architecture** | ⚠️ | Тот же принцип, домен в центре; разница терминологическая. Принят единый термин Clean Architecture для обоих концов |
| **Компонентно-ориентированный фронтенд (логика в компонентах); MVC как полная архитектура** | ❌ | Бизнес-правила связаны с фреймворком и UI: недостижимы покрытие ядра, итерации i18n/WCAG без переписывания, замена стека; MVC остаётся паттерном слоя адаптеров, а не архитектурой |
| **Бесструктурный монолит (папки по типу: controllers/, services/, models/)** | ❌ | Для длительно живущего сложного домена (109 требований, каскадные пересчёты) инварианты («маршрут — функция», «траектория всегда видна») размываются; тестирование ядра в изоляции невозможно |
| **CQRS/Event Sourcing как основной стиль** | ⚠️ | Механизм внутри принятой архитектуры (read-модели для `visualization`, in-process события + outbox из ADR модульного монолита), а не альтернатива слоистой структуре |

**Последствия:**

*Положительные:*
- **Ядро тестируется в изоляции** без UI/БД/сети: покрытие F1/F2 ≥ 90% + mutation testing реалистичны (`REQ-NFR-process.dev.test-coverage`).
- **Стек остаётся TBD без риска**: домен не зависит от фреймворка — любой кандидат (NestJS/FastAPI/Spring; React/Vue) ложится в те же круги без переписывания ядра; ADR `DES.STACK.*` (T3) свободны в выборе.
- **Граница VEDO Hub изолирована адаптерами**: смена форматов REST/MCP/SPARQL не затрагивает домен; contract tests на порту онтологии (`REQ-NFR-api.availability.hub-dependency-sla`).
- **Единый словарь на бэкенд и фронтенд**: симметричная структура и стратегия тестов, дешевле онбординг и передача знаний (bus-factor ≥ 2, `REQ-NFR-process.dev.developer-documentation`).
- **Тонкие адаптеры + чистое ядро** сохраняют бюджет p95 ≤ 200 мс: тяжёлые операции (маппинг, сериализация) локализованы на периферии.
- **UI заменяем итерациями**: WCAG AA, i18n (RU+EN), смена UI-фреймворка — без правок бизнес-правил (`REQ-NFR-ui.compliance.wcag-level`, `REQ-NFR-ops.compliance.i18n-readiness`).
- **Контуры Community/Enterprise разделяются конфигурацией и адаптерами**, а не доменом; безопасность (JWT, валидация) обрабатывается на входе, в адаптерах (`REQ-NFR-security.compliance.owasp-application-security`).
- **Согласуется с модульным монолитом**: модули = набор чистых кругов; события пересекают границы через порты.

*Отрицательные и смягчение:*
- **Бойлерплейт** (DTO, порты, мапперы) → смягчение: прагматичный минимализм — простые экраны/запросы проходят через Application-слой без избыточных церемоний; маппинг — только там, где форматы реально расходятся; контроль объёма в MVP.
- **Требует дисциплины границ** (нарушение Dependency Rule — главный риск) → смягчение: архитектурные тесты (dependency rules, arch-unit эквивалент) и линтеры в CI (`REQ-NFR-process.dev.engineering-gates`), чек-лист ревью, CC ≤ 10 (`REQ-NFR-process.dev.code-complexity`).
- **Применение Clean Architecture на фронтенде менее стандартизировано**, чем на бэкенде → смягчение: явные конвенции (состояние = слой use cases, DTO-маппинг в адаптерах, запрет бизнес-логики в компонентах) фиксируются в ADR репозиторной структуры (T5) и C4 component-диаграммах (T6).
- **Риск оверинжиниринга** для простых сценариев (справочные запросы, аутентификация) → смягчение: строгие круги применяются там, где есть доменная сложность; инварианты домена не обходятся никогда, но тонкие слои допускаются.
