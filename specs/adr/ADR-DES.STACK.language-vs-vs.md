# ADR-DES.STACK.language-vs-vs

**Статус:** ПРИНЯТО
**Дата:** 2026-08-02
**Контекст:** Выбор языка программирования для VEDO EduTrack (M0.1, T3)

Стиль зафиксирован в `ADR-DES.INFRA.modular-monolith-approach` (ПРИНЯТО): модульный монолит, 10 ограниченных контекстов как гексагональные модули, in-process событийная шина + outbox, read-модели (CQRS-light). Продукт — веб-приложение клиент-сервер (`REQ-NFR-infra.compliance.client-server-web-app`): тонкий SPA-клиент (карта знаний, дашборды, конструктор маршрутов) + серверное ядро. Детерминированное ядро (F1/F2: маршруты, лакуны, покрытие) + изолированный LLM-модуль (generate-and-validate). Команда работает в режиме вайбкодинга (AI-assisted разработка); стратегия качества — качественное тестирование и документация вместо опоры на языковой опыт команды. Enterprise-контур развёртывается on-premise сторонними заказчиками (152-ФЗ) — простота развёртывания критична.

**Ключевые драйверы:**
- p95 ≤ 200 мс при 1000 concurrent; SPARQL-пересчёт маршрута < 1 с (`REQ-NFR-api.performance.latency-p95`)
- Горизонтальное масштабирование: stateless, автоскейлинг ≤ 5 мин, 10× пик (`REQ-NFR-ops.performance.scalability`)
- Mutation testing ядра F1/F2: выживаемость мутантов ≤ 15% (`REQ-NFR-process.dev.test-coverage` — Stryker/PIT **или эквивалент**)
- i18n: RU+EN, ICU, добавление языка без кода (`REQ-NFR-ops.compliance.i18n-readiness`)
- Простота развёртывания/обслуживания для сторонних заказчиков (on-prem, SLA Enterprise ≤ 1 ч) (`REQ-NFR-ops.compliance.support-sla`)
- Детерминированное ядро + изолированный LLM-модуль; OWASP/JWT RS256 (`REQ-NFR-security.compliance.owasp-application-security`)

**Требование-источник:**
- `REQ-NFR-api.performance.latency-p95`
- `REQ-NFR-ops.performance.scalability`
- `REQ-NFR-process.dev.test-coverage`
- `REQ-NFR-ops.compliance.i18n-readiness`
- `REQ-NFR-ops.compliance.support-sla`
- `REQ-NFR-security.compliance.owasp-application-security`
- `REQ-NFR-infra.compliance.client-server-web-app`
- `REQ-NFR-infra.compliance.community-enterprise-isolation`

**Решение:**

Принять **Go** как язык бэкенда; фронтенд — TypeScript + React (см. `ADR-DES.STACK.framework-vs-vs`).

**Аргументы за Go:**

| # | Аргумент | Обоснование |
|---|----------|-------------|
| 1 | **Производительность под NFR** | Компилируемый код + goroutines: p95 ≤ 200 мс и SPARQL-пересчёт < 1 с достигаются с запасом; низкий memory footprint → дешёвые реплики. Каскады/outbox/webhooks — конкурентная модель Go естественна |
| 2 | **Один статический бинарник** | Прямое попадание в драйвер «простота развёртывания для сторонних заказчиков»: on-prem установка = копирование бинарника + PostgreSQL, без runtime/node_modules/JVM. Container = distroless, 10–20 МБ |
| 3 | **Границы модулей на уровне компилятора** | Go-пакеты + `internal/`: модули монолита не импортируют друг друга случайно — границы структурные, а не по конвенции. Для 10 контекстов это критично |
| 4 | **Простота языка → вайбкодинг** | Явная обработка ошибок (`if err != nil`), минимальный синтаксис без магии: AI генерирует более корректный Go (не может «молча проглотить» ошибку), меньше расхождений при генерации |
| 5 | **Встроенное тестирование** | `testing` из коробки + testcontainers-go (реальный PostgreSQL в CI) — стратегия «компенсация тестированием» поддержана нативно |
| 6 | **Экосистема под наш стек** | `pgx` — лучший Go-драйвер PostgreSQL; OTel Go SDK (зрелый); MCP SDK (Go); golangci-lint; Atlas/sqlc |
| 7 | **Практический кейс** | Hikasami: миграция NestJS→Go + PostgreSQL + GORM — тяжёлые запросы ускорились ~10× (десятки мс → <1 мс); 2–10 человек (наш масштаб) |

**Компромиссы и смягчение:**

| Компромисс | Смягчение |
|------------|-----------|
| Мутационное тестирование: gremlins/go-mutesting менее зрелы, чем Stryker/PIT (не названы в NFR) | NFR допускает «или эквивалент»; spike на M0.2 (оценка gremlins для ядра F1/F2); при слабости — компенсация арх-тестами + property-based + строгая стратегия unit/integration |
| i18n: go-i18n + `golang.org/x/text` ручнее, чем i18next | Достижимо: ICU MessageFormat (3 формы RU / 2 формы EN), дисциплина сканеров строк; основная масса строк — на фронте (react-i18next) |
| LLM-экосистема: нет LangChain-эквивалента, интеграции руками (`openai-go`) | LLM-модуль изолирован за портом (generate-and-validate), пост-MVP по триггеру (GPU/комплаенс) — вручную, но без загрязнения ядра |
| Два языка (Go-бэкенд + TS-фронт) | Классическая связка (Docker, Grafana, k8s); фронт в любом случае TS; общий контракт через OpenAPI |
| Меньше «из коробки» в веб-фреймворке (DI, валидация) | Компенсируется выбором инструментов: chi + wire (compile-time DI) + oapi-codegen; см. framework ADR |

**Рассмотренные альтернативы:**

| Альтернатива | Оценка | Причина отклонения |
|--------------|--------|--------------------|
| **TypeScript + NestJS** | ⚠️ | Сильные стороны: один язык клиент+сервер, Stryker (назван в NFR), i18next (лучший), авто-OpenAPI из декораторов, максимальный AI-корпус. Слабости: Node-runtime на on-prem (против драйвера простоты), границы модулей по конвенции (не компилятор), ниже потолок производительности. Кейс Hikasami: реальный уход с NestJS на Go при росте нагрузки |
| **Python + FastAPI** | ❌ | Сильные стороны: LLM/networkx. Слабости: динамическая типизация — слабые границы модулей монолита (риск «big ball of mud»), мутационное тестирование не названо в NFR (mutmut), i18n слабее, фронт всё равно TS (2 языка), производительность под p95 слабее |
| **Java + Spring Boot** | ❌ | Сильные стороны: сильнейшая типизация, PIT (назван в NFR), Enterprise-зрелость. Слабости: два языка, тяжёлый on-prem (JVM), медленнее итерации (Community-контур требует скорости), LLM-экосистема слабее, ICU4J громоздкий против i18next. Оправдан для чисто Enterprise-продукта — у нас два контура |

**Последствия:**

*Положительные:*
- Производительность и деплой: p95/SPARQL-тайминги с запасом; on-prem = один бинарник (сильнейший аргумент для сторонних заказчиков).
- Границы модулей структурные: модульный монолит из 10 контекстов защищён компилятором + арх-лингерами (depguard).
- Вайбкодинг: явный синтаксис → надёжная AI-генерация; встроенный testing → стратегия качества.
- Экосистема: pgx, OTel, testcontainers — всё зрелое под наш стек.

*Отрицательные и смягчение:*
- Молодое мутационное тестирование → spike M0.2 + компенсация тестами (см. выше).
- i18n-гигиена ручнее → дисциплина go-i18n, масса строк на фронте.
- LLM руками → изолированный порт, пост-MVP.
- Ручной DI/структура → wire + арх-тесты в CI (engineering-gates).
