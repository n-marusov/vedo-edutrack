# ADR-DES.SECURITY.rbac-model

**Статус:** ПРИНЯТО
**Дата:** 2026-08-02
**Контекст:** Модель ролевого доступа (RBAC) VEDO EduTrack (M0.1, T5)

EduTrack — клиент-серверное приложение с двумя контурами развёртывания (`REQ-NFR-infra.compliance.community-enterprise-isolation`): **Community** (публичная онтология, семейное обучение, EdTech-платформы) и **Enterprise** (корпоративный, on-prem/private cloud, 152-ФЗ, SSO). Персоны из `specs/vision.md` §3.1: родитель, ученик, учитель/методист, директор школы, CTO/CPO EdTech-платформы, HR/L&D-руководитель, сотрудник; контрибьюторские роли (методист-контрибьютор, сопровождающий онтологии) — **роли VEDO Hub, не EduTrack** (EduTrack не редактирует онтологии).

Требование `REQ-NFR-security.compliance.role-based-access` фиксирует базовые роли: **learner, parent, school director, methodologist, HR** — и правила scope: родитель — только свои дети, директор — только своя школа, HR — только свой департамент. Проверка роли и scope — **на серверной стороне**, не только в UI. `REQ-FR-api.sso.keycloak`: Enterprise SSO через Keycloak (OIDC/SAML 2.0), роли IdP маппятся на роли EduTrack. Стек (T3): Go + chi, JWT RS256/JWKS (`lestrrat-go/jwx`), Keycloak — пост-MVP адаптер за портом identity (`ADR-IMPL.PROCESS.development-tooling` §5).

Архитектура — модульный монолит + Clean Architecture (`ADR-DES.INFRA.modular-monolith-approach`, `ADR-DES.INFRA.clean-architecture-adoption`): аутентификация/авторизация обрабатывается на входе (адаптеры), бизнес-правила доступа — в домене (`identity-access`), энфорсмент — на API-границе и в Application-слое.

**Ключевая проблема дизайна:** модель не должна зашивать конкретные бизнес-роли (learner, methodologist, HR…) — иначе движок авторизации привязан к одному бизнес-кейсу, и любая новая роль, контур или продукт платформы требует изменения кода. RBAC разделяется на два уровня: **абстрактный движок** (инвариант, переиспользуемый для любого продукта/контура) и **каталог ролей** (данные-конфигурация конкретного продукта).

**Требование-источник:**
- `REQ-NFR-security.compliance.role-based-access` (роли, scope, серверный энфорсмент, TTL прав ≤ 15 мин)
- `REQ-FR-api.sso.keycloak` (SSO OIDC/SAML, маппинг ролей IdP)
- `REQ-NFR-security.compliance.owasp-application-security` (JWT RS256/JWKS, rate limiting)
- `REQ-NFR-security.compliance.pii-152-fz` (Enterprise: доступ к PII — по ролям, аудит)
- `REQ-NFR-infra.compliance.community-enterprise-isolation` (два контура, разные наборы ролей/scope)
- `REQ-NFR-data.compliance.pii-export-deletion` (PII-экспорт/удаление — права администратора/HR)
- `REQ-NFR-ops.access.production-control` (2-person rule, JIT-доступ для ops)

**Решение:**

Принять **двухслойную RBAC-модель: абстрактный движок + каталог ролей как данные**.

### Слой 1. Generic RBAC engine (инвариант модели)

Пять абстрактных сущностей:

| Сущность | Определение |
|----------|-------------|
| **Subject** | Субъект доступа: учётная запись пользователя или сервисный principal (API-ключ/сервис-аккаунт) |
| **Role** | Именованный набор разрешений. Роль — **данные** (строка каталога), не тип в коде |
| **Permission** | Пара `resource × action`, action ∈ {C, R, U, D, execute} |
| **Grant** | Связь «роль → разрешение» (таблица `role_permissions`) |
| **Assignment** | Связь «субъект → (роль, scope)»: пользователь получает роль с областью видимости |

Правила движка:

1. **Роли — данные, не код**: роль определяется записями каталога (`roles` + `role_permissions`); движок не знает конкретных ролей на этапе компиляции. Новая роль / изменение прав = строка в БД (миграция/сид), без изменения кода и перезапуска сервиса.
2. **Deny-by-default**: доступ разрешён только при явном grant (роль × resource × action × scope); по умолчанию — отказ.
3. **Композиция ролей — опциональна и data-driven**: роль может включать другую роль (поле `includes`); предпочтение — плоские наборы прав (детерминированная тест-матрица), композиция допускается для операционных ролей (например, `admin` = продуктовые read-права + системные права).
4. **Generic scope-предикаты** (второй уровень проверки после роли):

   | Scope | Семантика | Пример в EduTrack |
   |-------|-----------|-------------------|
   | `own` | Ресурсы субъекта | профиль, маршрут, прогресс ученика |
   | `dependents` | Ресурсы подопечных субъекта | дети (родитель), сотрудники в подчинении |
   | `unit` | Ресурсы организационной единицы (дерево) | класс/группа (учитель), школа (директор), департамент (HR) |
   | `all` | Системный scope (только для admin/ops по JIT) | вся система |

   Предикат вычисляется **на серверной стороне** для каждого ресурса; нарушение → `403` (или `404` для несуществующих — без раскрытия информации, `REQ-NFR-security.compliance.role-based-access`).
5. **Энфорсмент — серверный**: JWT RS256/JWKS на входе (адаптеры), permission + scope в Application-слое для каждого use case с ресурсом, инварианты в Domain, UI — только UX-слой (никогда не источник доверия), аудит PII-операций.
6. **Кэш прав**: in-memory, TTL ≤ 15 мин — изменение роли/увольнение/перевод применяется ≤ 15 мин без рестарта; инвалидация по claim `roles` + короткий TTL access-токена (15–60 мин) + refresh-ротация.
7. **SSO-маппинг — конфигурация**: соответствие «роль IdP → роль платформы» (Keycloak OIDC/SAML) — данные конфигурации, не код; обновляется при каждом SSO-входе.
8. **Один движок — много каталогов**: контуры Community/Enterprise и будущие продукты используют тот же движок; различие — в каталогах ролей и конфигурации, не в коде.

### Слой 2. Каталог ролей (данные, конфигурация)

Каталог живёт в `identity_access` (таблицы `roles`, `role_permissions`; сид-миграции) и наполняется per-product.

**Архетипы ролей** — контрактный слой модели: универсальный, продукт-агностический набор паттернов доступа (permission set + scope). Архетипы фиксированы моделью; роли конкретного продукта — **экземпляры архетипов** (данные каталога). Контракт RBAC (NFR `role-catalog`, `permission-matrix`) привязан к архетипам, а не к именам ролей — новый продукт/контур комбинирует существующие архетипы без изменения модели и контракта:

| Архетип | Семантика |
|---------|-----------|
| `self` | Доступ к собственным данным (профиль, маршрут, прогресс) |
| `dependents-owner` | Доступ к данным подопечных (дети, подчинённые) |
| `staff` | Работа с группами/классами в рамках `unit` |
| `management` | Управление `unit` (школа/департамент): отчётность, назначения, покрытие |
| `integration` | API/service-доступ: ключи, webhooks, лимиты |
| `admin` | Администрирование системы: пользователи, роли, конфигурация, аудит |
| `ops` | Производственный доступ: инфраструктура, деплой, БД (2-person rule, JIT, вне продуктовых ресурсов) |

**Начальный каталог EduTrack** (сид, из `REQ-NFR-security.compliance.role-based-access` + персон `vision.md` §3.1):

| Роль (сид) | Архетип | Описание | Контур | Scope по умолчанию |
|------|----------|----------|--------|--------------------|
| `learner` | `self` | Ученик (семейное обучение, школа, сотрудник корпорации) | Community + Enterprise | `own` — профиль, маршрут, план, прогресс, траектория, лакуны, покрытие |
| `parent` | `dependents-owner` | Родитель/аккаунт-владелец (семейное обучение) | Community | `dependents` — свои дети (профили, маршруты, планы, прогресс, отчёты) |
| `teacher` | `staff` | Учитель (работает с классом/группой) | Community (Pro) | `unit` — свои классы/группы учеников |
| `methodologist` | `staff` + `management` | Методист (маршруты, планы, покрытие ФГОС) | Community + Enterprise | `unit` — организация/подразделение |
| `school-director` | `management` | Директор частной школы (отчётность, группы) | Community (Pro) | `unit` — своя школа (все ученики, отчёты, покрытие) |
| `hr-manager` | `management` | HR/L&D-руководитель (онбординг, карьерные треки, отчётность) | Enterprise | `unit` — свой департамент |
| `employee` | `self` | Сотрудник корпорации (онбординг-маршрут) | Enterprise | `own` — профиль, план, прогресс |
| `platform-integrator` | `integration` | CTO/CPO EdTech-платформы (API-доступ, webhooks) | Community (Pro) | `own` — API-ключи, подписки webhook, лимиты |
| `admin` | `admin` | Администратор системы (пользователи, роли, конфигурация, аудит) | Оба | `all` (операционная роль, не продуктовая) |
| `ops` | `ops` | Операционная роль (производственный доступ: 2-person rule, JIT) | Оба | `all` (только инфраструктура, вне продуктовых данных) |

**Маппинг персон vision.md §3.1 → архетипы (контракт) → роли (сид-данные, детализация — в RBAC-матрице T8):**

| Персона (§3.1) | Роль EduTrack |
|----------------|---------------|
| Родитель (семейное обучение) | `parent` |
| Ученик (семейное обучение) | `learner` |
| Учитель / методист | `teacher` + `methodologist` |
| Директор частной школы | `school-director` |
| CTO/CPO EdTech-платформы | `platform-integrator` |
| HR-директор / L&D-руководитель | `hr-manager` |
| Сотрудник (корпорация) | `employee` |
| Методист-контрибьютор | *(роль VEDO Hub — не EduTrack)* |
| Сопровождающий публичной онтологии | *(роль VEDO Hub — не EduTrack)* |

Контрибьюторские роли живут в VEDO Hub (EduTrack не редактирует онтологии); EduTrack предоставляет им read-доступ к онтологии через `ontology-port` (read-only), но не управляет их правами в Hub.

**NFR-обязательство каталога:** каталог EduTrack обязан содержать роли-экземпляры архетипов `learner` (`self`), `parent` (`dependents-owner`), `school-director` (`management`), `methodologist` (`management`), `hr-manager` (`management`) — проверяется конфиг-гейтом/тестом — `REQ-NFR-security.compliance.role-based-access`. Это требование к **данным каталога** (сид), не к модели: имена ролей — данные, контракт привязан к архетипам.

### Контуры: Community vs Enterprise (конфигурация каталога)

| Аспект | Community | Enterprise |
|--------|-----------|------------|
| Каталог ролей | `learner`, `parent`, `teacher`, `methodologist`, `school-director`, `platform-integrator`, `admin`, `ops` | `learner`(=`employee`), `methodologist`, `hr-manager`, `admin`, `ops` (+ маппинг IdP-ролей через Keycloak) |
| Аутентификация | Локальные учётные записи (email+пароль, JWT RS256/JWKS) | SSO через Keycloak (OIDC Authorization Code + PKCE, SAML 2.0 SP-initiated), роли IdP → роли EduTrack (`REQ-FR-api.sso.keycloak`) |
| PII | Общий периметр, 152-ФЗ | Усиленный: PII-доступ по ролям, аудит, локализация (242-ФЗ) |
| Isolation | Tenant-колонка/схемы | Полная изоляция кластера (on-prem) |

Единый API-контракт обоих контуров (`REQ-NFR-infra.compliance.community-enterprise-isolation`) — RBAC различается **конфигурацией каталога** (набор ролей, scope, IdP), не кодом.

### Enforcement points (серверный энфорсмент)

```
Client → [API Gateway/chi middleware] → [Application layer] → [Domain]
            │                                │
            ├─ JWT-валидация (RS256/JWKS)    ├─ Scope-проверка (resource owner check)
            ├─ роль + разрешение (R/W кэш)   ├─ объектные инварианты
            ├─ rate limiting (429)           └─ аудит-запись (identity, action, resource)
            └─ 401/403 (без раскрытия)
```

1. **Адаптеры API (вход)**: JWT-валидация (RS256, `/.well-known/jwks.json`), извлечение claims (`sub`, `roles`, `scope`), rate limiting (`REQ-NFR-security.compliance.owasp-application-security`).
2. **Application-слой**: проверка разрешения (role × resource × action) + **scope-проверка** (владелец ресурса/организации) — обязательна для каждого use case, работающего с ресурсом. Ошибка → `403`; несуществующий ресурс → `404` (без раскрытия).
3. **Domain**: инварианты домена (например, родитель не может фиксировать план ребёнка без согласия — если таковое определено), не зависят от RBAC.
4. **UI (фронтенд)**: скрытие/блокировка элементов — **только UX-слой**, никогда не источник доверия (сервер — единственный энфорсер).
5. **Аудит**: операции с PII и правами (назначение роли, экспорт/удаление PII, изменение scope) пишутся в журнал аудита (`REQ-NFR-security.compliance.pii-152-fz`, `REQ-NFR-data.compliance.pii-export-deletion`).

### Разрешения по умолчанию — deny

- По умолчанию — **deny-all**; права выдаются явными grants (роль × resource × action × scope).
- `ontology-read` — read-only (EduTrack не редактирует онтологию; граница с Hub — `ontology-port` ACL).
- Webhook/LMS/API-доступ `platform-integrator` — только через API-ключи с ограничением прав (read route/progress/coverage + configure webhooks), не пользовательские роли.

**Рассмотренные альтернативы:**

| Альтернатива | Оценка | Причина отклонения |
|--------------|--------|--------------------|
| **Зашитые бизнес-роли в модели** (роли как типы кода) | ❌ | Привязывает движок к одному бизнес-кейсу: новая роль/контур/продукт = изменение кода и релиз; дублирование прав в коде и конфиге; каталог-как-данные решает это без затрат |
| **ABAC (attribute-based) как основная модель** | ⚠️ | Мощнее (атрибуты: время, IP, отношения), но сложнее в аудите/тестах и вайбкодинге; на MVP достаточно RBAC + scope (это и есть простая форма ABAC — `own`/`dependents`/`unit`); ABAC-атрибуты добавляются точечно, если появятся (например, регион, тип лицензии) |
| **Иерархия ролей с наследованием (role hierarchy)** | ⚠️ | Привычна (methodologist > teacher > learner), но наследование усложняет тест-матрицу и аудит; принята data-driven композиция (`includes`) как опциональный механизм при предпочтении плоских наборов прав |
| **Policy engine (OPA/CASL)** | ⚠️ | CASL — хорош для фронта, OPA — мощный для серверной политики; на MVP объём прав невелик (7 архетипов × 11 ресурсов) — таблица `role_permissions` + код-проверки проще и стабильнее для вайбкодинга; OPA — пост-MVP по триггеру (сложные кросс-ресурсные политики) |
| **Фронтенд-энфорсмент без серверной проверки** | ❌ | Прямое нарушение `REQ-NFR-security.compliance.role-based-access` («проверка на серверной стороне»); UI — только UX-слой |
| **Роли только в JWT без БД-каталога** | ⚠️ | Роли в JWT — да (claims), но набор прав (роль × resource × action) и каталог — в БД (`identity_access.roles`, `role_permissions`), чтобы менять права без пересборки/перевыпуска токенов; JWT содержит только ссылку на роли |
| **Собственная SSO-реализация вместо Keycloak** | ❌ | Enterprise-требование — SAML 2.0 + OIDC из коробки; Keycloak — стандарт, экономит разработку и соответствует `REQ-FR-api.sso.keycloak`; собственная реализация SAML — дорого и рискованно (security) |

**Последствия:**

*Положительные:*
- **Абстрактная модель, переиспользуемая модель**: движок (Role/Permission/Scope/Assignment) не привязан к EduTrack — любой продукт/контур платформы получает RBAC из коробки, меняя только каталог.
- **Выполнение NFR**: архетипы `self`/`dependents-owner`/`management` покрыты ролями-экземплярами (learner/parent/school-director/methodologist/hr-manager) — гарантировано конфиг-гейтом каталога; scope-правила + серверный энфорсмент — 100% критериев `REQ-NFR-security.compliance.role-based-access` (тест-матрица архетип × ресурс в CI).
- **Эволюция ролей без кода**: новая роль, изменение прав, новый контур = миграция/сид каталога, без релиза движка; изменение прав ≤ 15 мин без рестарта (кэш TTL).
- **Два контура — один код**: каталоги Community/Enterprise — конфигурация (`REQ-NFR-infra.compliance.community-enterprise-isolation`) без дублирования.
- **Enterprise SSO**: Keycloak (OIDC + SAML) за портом identity, маппинг ролей IdP — конфигурация (`REQ-FR-api.sso.keycloak`).
- **Архетипы ускоряют проектирование**: `self`/`dependents-owner`/`staff`/`management`/`integration`/`admin`/`ops` — готовые паттерны для каталогов новых продуктов.
- **Аудит PII-операций**: назначение ролей, экспорт/удаление PII — журналируются (152-ФЗ).
- **Вайбкодинг-стабильность**: детерминированная модель (Role/Permission/Scope + каталог-данные) — легко генерировать код, сид-миграции и тесты.

*Отрицательные и смягчение:*
- **Каталог как данные требует валидации** → смягчение: конфиг-гейт (NFR-роли обязательны), тест-матрица enforcement в CI (позитив/негатив по каждой роли каталога, обход scope → 403/404), сид-миграции ревьюятся как код.
- **Плоская RBAC → больше строк в role_permissions** → смягчение: 7 архетипов × 11 ресурсов (сид-роли — экземпляры) — малая таблица; генерация прав из архетипов и RBAC-матрицы T8.
- **Scope-проверки в каждом use case — риск пропуска** → смягчение: архитектурные тесты (каждый use case с ресурсом имеет scope-check), test-матрица enforcement.
- **JWT-claims устаревают при смене роли** → смягчение: короткий TTL access (15–60 мин) + refresh-ротация + TTL-кэш прав ≤ 15 мин (двойное покрытие).
- **Композиция ролей усложняет аудит** → смягчение: композиция только для операционных ролей, плоские наборы — по умолчанию; аудит фиксирует материализованный набор прав.
- **Keycloak — пост-MVP**: на MVP — локальные учётные записи с тем же движком → миграция на SSO без переписывания (порт identity).
- **Admin/ops требуют дисциплины** → смягчение: 2-person rule, JIT-доступ, аудит (`REQ-NFR-ops.access.production-control`), разделение продуктовых и операционных прав.
