# REQ-NFR-security.compliance.owasp-application-security

**Приоритет:** P0
**Ключевая функция:** cross-cutting (все функции)
**Источник:** quality-matrix audit ячейка 4.2 (Аварии/Эксплуатация), vision 1.8 (бизнес-риски), OWASP Top 10 (2021); урок опыта: утечки ПДн с оборотными штрафами по 152-ФЗ (2025)

**Описание:** Требование закрывает лакуну «Аварии/Эксплуатация» матрицы программирования качества: система должна защищать данные и функции от атак и некорректного ввода — rate limiting, защита от DDoS, обработка некорректного ввода, соответствие OWASP Top 10.

**Критерии приёмки:**
- Rate limiting: API-эндпоинты ограничивают частоту запросов (например, ≤ 100 запросов/мин на API-ключ для REST API; SPARQL — ≤ 10 запросов/мин); превышение → `429 Too Many Requests` с заголовком `Retry-After`.
- Обработка некорректного ввода: все поля API валидируются (схема, типы, длины, диапазоны); невалидный ввод → `400 Bad Request` без выполнения бизнес-логики.
- Защита от OWASP Top 10: автоматическое сканирование зависимостей и кода (SAST/DAST) в CI — 0 критических и высоких уязвимостей перед релизом.
- Инъекции: SPARQL-запросы параметризованы; пользовательский ввод никогда не конкатенируется в запросы (тест-сьют на injection).
- Аутентификация и авторизация: JWT-токены валидируются по алгоритму RS256 с публичным ключом из `/.well-known/jwks.json` (детерминированный алгоритм проверки).
- Защита от DDoS: rate limiting на уровне API-шлюза + circuit breaker на Hub API (см. REQ-NFR-api.availability.hub-dependency-sla).
