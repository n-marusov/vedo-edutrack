# REQ-NFR-ops.observability.golden-signals-dashboards

**Приоритет:** P0
**Ключевая функция:** cross-cutting (операции/observability)
**Источник:** quality-matrix audit ячейки 2.3/3.3/5.3 (Эргономика/Функции/Тех.обеспеченность — Сопровождение), Google SRE (four golden signals); урок опыта: Knight Capital 2012 — состояние системы не контролировалось в реальном времени

**Описание:** Система обязана предоставлять операторам (DevOps/SRE) консоли мониторинга: сводный SLO-борд и сервисные дашборды, отражающие «золотые сигналы» (latency, traffic, errors, saturation) для каждого сервиса и эндпоинта, — чтобы состояние сервиса оценивалось без ручной сборки метрик. Требование закрывает лакуну «Эргономика/Сопровождение» (ячейка 2.3): эргономика инструментов сопровождения для операторов.

**Критерии приёмки:**
- Существует SLO-борд: доступность, доля ошибок и текущий burn rate по каждому SLO; время актуализации данных ≤ 30 секунд.
- Существуют сервисные дашборды: для каждого сервиса/эндпоинта отображаются 4 золотых сигнала — latency (p50/p95/p99), traffic (RPS), errors (5xx/4xx), saturation (CPU, память, длина очереди).
- Покрытие: дашборды существуют для 100% сервисов и публичных эндпоинтов.
- Время открытия любого дашборда ≤ 3 секунды; права: операторы — read-only, владельцы сервисов — полный доступ.
- Метрики дашбордов совпадают с метриками Prometheus из REQ-NFR-api.performance.latency-p95 (расхождение значений = 0).
