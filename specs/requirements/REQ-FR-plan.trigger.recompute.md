# REQ-FR-plan.trigger.recompute

**Приоритет:** P0
**Ключевая функция:** F1.2
**Источник:** UC-plan.compute.recompute-on-progress; UC-plan.compute.recompute-on-goal-change; vision.md F1.2, P2, P8
**Описание:** Система пересчитывает маршрут при наступлении событий-триггеров: (1) прогресс ученика — событие `module.mastered` (вебхук из LMS/платформы или внутреннее подтверждение освоения) → пересчёт множества доступных модулей и маршрута целиком; (2) обновление онтологии (методист добавил тему/связь) → каскадный пересчёт всех затронутых маршрутов; (3) смена цели («хочу в IT» → «хочу в геймдизайн») → полная перестройка маршрута от текущей позиции к новой цели (событие `GoalChanged`); (4) периодическая еженедельная проверка «что нового доступно». Повторная доставка события с тем же `idempotencyKey` не приводит к двойному пересчёту. После каждого пересчёта публикуется `RouteRecalculated`, запускается каскад F1.6, и факт пересчёта логируется с идентификатором породившего события (трассируемость).

**Критерии приёмки:**
- Латентность: для события `module.mastered` с корректным `idempotencyKey` время «событие → завершённый пересчёт маршрута» ≤ 5 с; после пересчёта 100% модулей со всеми освоенными strict-пререквизитами попадают в ближний горизонт.
- Идемпотентность: повторная доставка события с тем же `idempotencyKey` (до 3 дублей) приводит ровно к одному пересчёту — 0 повторных изменений позиции и 0 повторных публикаций `RouteRecalculated`.
- Смена цели порождает `GoalChanged` и полную перестройку маршрута: новый маршрут вычисляется от текущей позиции к новой цели на зафиксированной версии онтологии (0 шагов, унаследованных от маршрута старой цели).
- Обновление онтологии пересчитывает все затронутые маршруты (содержащие изменённый модуль/связь) в течение ≤ 15 мин после публикации обновления; незатронутые маршруты не пересчитываются (0 лишних пересчётов).
- Периодическая проверка «что нового доступно» выполняется с интервалом 7 суток ± 12 ч и пересчитывает маршрут только при появлении новых доступных модулей; иначе версия расчёта не меняется (0 пересчётов без изменения входных данных).
- Освоение ниже порога подтверждения (например, < 70% с учётом погрешности) не переводит модуль в статус «освоен» и не запускает пересчёт — фиксируется только прогресс (0 пересчётов по неподтверждённому освоению).
- Трассируемость: 100% логов пересчёта содержат идентификатор породившего события (eventId) и версию онтологии расчёта.
