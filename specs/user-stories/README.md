# Пользовательские истории VEDO EduTrack

В этой директории находятся пользовательские истории (User Stories) проекта VEDO EduTrack — сервиса образовательных маршрутов на базе VEDO Hub. Все истории оформлены в формате Gherkin.

## Структура

- `README.md` — данный файл с описанием требований к разработке пользовательских историй
- `_matrix.md` — матрица связей пользовательская история → прецедент использования
- `US-<domain>.<subdomain>.<action>.md` — отдельные файлы пользовательских историй с семантическими идентификаторами

## Семантическая классификация US

Идентификаторы пользовательских историй построены по иерархическому принципу, аналогично UC:

```
US-<domain>.<subdomain>.<action>
```

Домен соответствует прецеденту использования (UC), что облегчает навигацию и трассировку:

| Домен | Соотв. функции (vision.md) | Описание | Примеры |
|-------|---------------------------|----------|---------|
| `US-plan.*` | F1. Планирование маршрута | Вычисление маршрута, триггеры перестройки, три горизонта, подбор ресурсов, анализ разрыва до цели, каскад пересчёта, педагогическая концепция, фиксация плана, пересчёт плана, синхронизация расписания, входные ограничения (чекпоинты и ФГОС) | `US-plan.compute.shortest-path` |
| `US-execute.*` | F2. Исполнение плана | Диагностика лакун, проверочные задания и калибровка, сверка знания с формальной рамкой, план-факт, прогноз выполнения, уведомления об отклонениях, покрытие ФГОС и дефициты, аттестационная готовность | `US-execute.progress.plan-vs-actual` |
| `US-resource.*` | F3. Ресурсы | Привязка ресурсов к модулям, подбор под ученика, доступность и обеспеченность, затраты и бюджет маршрута | `US-resource.catalog.filter-by-format` |
| `US-viz.*` | F4. Визуализация | Карта знаний (2D-граф с прогрессом), дашборд ученика, конструктор маршрутов, дашборд родителя/HR/методиста, карта лакун, панель группы | `US-viz.map.knowledge-graph` |
| `US-practice.*` | F5. Связь с практикой и жизнью | Истории и контекст к модулям, проектные идеи, рекомендации при освоении, карта качеств | `US-practice.stories.recommend` |
| `US-api.*` | F6. Интеграции | REST API, SPARQL endpoint, коннекторы к LMS, webhooks, SSO/SAML, MCP-сервер | `US-api.rest.compute-route` |
| `US-a11y.*` | — (сквозная) | Доступность: screen reader, keyboard-only навигация | `US-a11y.navigation.map-reader` |

## Формат описания

Все пользовательские истории оформлены единым Gherkin-шаблоном:

```gherkin
@US-<domain>.<subdomain>.<action> @UC-... @P...
Feature: US-<domain>.<subdomain>.<action> <краткое название>

  Background:
    Given <общие предусловия>

  Scenario: <основной пользовательский результат>
    Given <контекст>
    When <действие пользователя или системы>
    Then <ожидаемый результат>
```

### Теги

Каждая история содержит теги:
- `@US-<domain>.<subdomain>.<action>` — семантический идентификатор пользовательской истории
- `@UC-...` — идентификатор связанного прецедента использования
- `@P0`/`@P1`/`@P2` — приоритет (P0 — критический, P1 — важный, P2 — желательный)
- Дополнительные теги для фильтрации: `@plan`, `@execute`, `@resource`, `@viz`, `@practice`, `@api`, `@accessibility`

## Требования к разработке пользовательских историй

### 1. Структура и именование

- Каждый файл содержит одну пользовательскую историю или один сквозной сценарий.
- Имя файла соответствует семантическому идентификатору: `US-<domain>.<subdomain>.<action>.md`.
- Файл начинается с заголовка первого уровня (`#`) с полным идентификатором и названием.
- Теги Gherkin указываются в первой строке сценария.
- Идентификатор вешается якорем (`<a id="us-<domain>.<subdomain>.<action>"></a>`) перед заголовком для кросс-ссылок.

### 2. Содержание

- **Background** описывает общие предусловия для всех сценариев истории.
- **Scenario** описывает один конкретный пользовательский результат.
- Шаги `Given` задают контекст и предварительные условия.
- Шаги `When` описывают действие пользователя или системы.
- Шаги `Then` проверяют ожидаемый результат.
- Для проверки альтернативных потоков (негативные сценарии) используется отдельный Scenario.

### 3. Язык

- Все пользовательские истории пишутся **на русском языке**.
- Названия сущностей, свойств и технические идентификаторы — на английском (например, `Learner`, `Route`, `Gap`, `Mastery`, `Checkpoint`, `hasStrictPrerequisite`).
- Сообщения об ошибках, возвращаемые системой, указываются в кавычках на языке системы (английский).

### 4. Приоритеты

- **P0** — критические сценарии, без которых продукт не может быть выпущен (например, построение маршрута, диагностика лакуны, базовая карта знаний).
- **P1** — важные сценарии, закрывающие ключевые потребности пользователей (например, план-факт, покрытие ФГОС, REST API).
- **P2** — желательные сценарии, улучшающие пользовательский опыт (например, подбор ресурсов по стилю обучения, детализированные дашборды).

### 5. Связи

- Каждая история должна быть связана с прецедентом использования (Use Case) через матрицу связей `_matrix.md`.
- Каждая история должна иметь назначенный приоритет.

- Ключевые функции из `vision.md` трассируются через UC: каждая история в конечном счёте восходит к одной или нескольким функциям (F1–F6).

### 6. Специфика EduTrack

- **Маршрут — это функция, а не документ**: истории на вычисление маршрута (`US-plan.*`) описывают идемпотентные пересчёты, а не CRUD-операции над сущностью.
- **Внешняя онтология**: VEDO EduTrack не хранит онтологии — она читает их через VEDO Hub. Истории не должны описывать редактирование онтологии; для этого существуют US проекта VEDO Core.

- **События предметной области**: `module.mastered`, `plan.deviated`, `route.recomputed` — это триггеры для пересчётов, и истории должны явно описывать эти каскады.

### 7. Accessibility (доступность)

- Истории с тегами `@accessibility` описывают сценарии для пользователей, использующих screen reader (NVDA / VoiceOver) или keyboard-only навигацию.
- Все сценарии доступности должны быть реализованы в соответствии с WCAG MVP.
- Особое внимание — к визуализациям: карта знаний и карта лакун должны иметь текстовые альтернативы и keyboard-доступную навигацию.
